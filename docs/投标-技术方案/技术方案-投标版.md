# 第一章 项目需求分析

## 1.1 项目建设背景

### 1.1.1 政策背景

近年来，国家高度重视住房保障体系建设，"租购并举"成为住房制度改革的核心方向。《国务院办公厅关于加快发展保障性租赁住房的意见》（国办发〔2021〕22号）明确提出加快完善以公租房、保障性租赁住房和共有产权住房为主体的住房保障体系；河南省、郑州市相继出台保障性租赁住房筹集建设与运营管理办法，要求以数字化手段提升保障性住房分配、运营、监管的效率与公平性。

郑州航空港经济综合实验区作为国家级航空经济先行区，产业人口快速集聚，人才公寓、保障性租赁住房、市场化租赁住房的供给规模持续扩大。传统依靠线下窗口受理、纸质档案管理、人工对账的房屋管理模式，已难以支撑多项目、多业态、大体量的租赁业务运营需求。

本项目建设所依据的主要政策文件如下表所示：

| 层级 | 政策文件 | 与本项目的关联要点 |
|---|---|---|
| 国家 | 《国务院办公厅关于加快发展保障性租赁住房的意见》（国办发〔2021〕22号） | 明确保障性租赁住房基础制度与支持政策，要求提升租赁住房管理服务水平 |
| 国家 | 《"十四五"公共服务规划》 | 要求扩大保障性租赁住房供给，完善住房保障服务体系 |
| 国家 | 《关于加强新市民、青年人等群体住房保障工作的意见》 | 聚焦新市民、青年人住房困难问题，要求简化准入审核流程 |
| 国家 | 《"数字中国"建设整体布局规划》 | 要求推进公共服务数字化、普惠化，政务服务"一网通办" |
| 行业 | 《住房和城乡建设部关于加强轻资产住房租赁企业监管的意见》 | 对租赁资金、租金监管提出规范化要求 |
| 河南省 | 《河南省加快发展保障性租赁住房实施方案》 | 明确全省保租房筹集目标与运营管理要求 |
| 郑州市 | 《郑州市保障性租赁住房运营管理办法》 | 规定保租房申请条件、审核程序、租金标准、退出机制 |
| 郑州市 | 《郑州市人才公寓建设管理办法》 | 规定人才公寓的申请资格、配租程序、优惠政策 |
| 港区 | 郑州航空港经济综合实验区保租房、人才公寓管理现行办法 | 本项目资格校验、配租流程、租金政策的直接业务依据 |
| 数字政务 | 郑州市"郑好办"一体化政务服务平台建设要求 | 要求各类民生服务接入郑好办统一用户体系，实现"一次认证、全网通办" |

从政策导向可以看出：**住房保障业务的"数字化、平台化、协同化"是明确的建设方向**——资格审核要与政务数据打通实现"免证明"，业务办理要向移动端迁移实现"掌上办"，运营管理要以数据为支撑实现"精细化"。本项目正是上述政策要求在郑州航空港经济综合实验区住房租赁领域的具体落地。

### 1.1.2 业务背景

郑州数据集团有限公司承担着区域房屋租赁业务的数字化运营职责。当前房屋租赁管理业务面临以下现实问题：

1. **业务流程线上化程度不足**：选房、签约、入住、退租、续租、缴费等核心业务环节仍存在线下办理、人工流转的情况，租户往返跑腿多、办理周期长；
2. **多业态管理口径不统一**：人才公寓、保租房、市场租赁三类业务在资格条件、配租方式、租金标准、审批流程上各不相同，缺乏统一的系统化承载；
3. **数据孤岛问题突出**：房源、合同、账单、租户数据分散管理，与郑好办用户体系、政务资格核验数据、支付渠道、电子签章等外部系统未打通，资格审核依赖人工线下核查；
4. **运营决策缺乏数据支撑**：出租率、收缴率、逾期率等关键经营指标无法实时统计，管理层缺少直观的数据看板；
5. **存量数据亟需迁移整合**：现有系统中的房屋、合同、账单、用户等港区业务数据需要平滑迁移至新系统，保证业务连续性。

上述问题对各方主体的影响分析如下：

| 影响对象 | 现状问题带来的影响 | 数字化改造后的预期改善 |
|---|---|---|
| 租户（个人） | 资格审核周期长，需线下提交证明材料；选房、签约、缴费需多次跑现场；办理进度不透明 | 政务数据自动核验"免证明"，全流程掌上办理，进度实时可查 |
| 企业客户 | 批量入住/退租依靠线下名单流转，办理效率低、易出错 | 名单模板在线上传、批量办理，审批流程线上留痕 |
| 运营管理人员 | 房源台账手工维护，配租组织依靠电话与表格，审批流转慢 | 房源状态实时联动，配租批次在线管理，审批一键流转 |
| 财务人员 | 对账依赖人工核对流水，退款流程长，开票手工登记 | 支付渠道自动对账，退款在线审批，开票申请与交付线上化 |
| 管理决策层 | 经营数据靠事后统计报表，时效性差、口径不一 | 数据看板实时呈现出租率、收缴率、逾期率等核心指标 |
| 监管与审计 | 纸质档案调阅困难，操作过程难以追溯 | 全流程电子留痕，操作日志可查可追溯 |

### 1.1.3 项目定位

本项目通过采购研发团队驻场开发服务，构建包含**房源管理、合同管理、优惠券管理、消息管理、个人中心、运营中心、支付管理、数据看板**等业务的房屋管理系统，覆盖**移动端、小程序端、微信公众号端、后台管理端**四端，实现房屋租赁业务"申请—选房—签约—入住—居住服务—退租—结算"全生命周期线上化闭环，打造"数据多跑路、群众少跑腿"的智慧化房屋管理服务平台。

围绕上述定位，我方将本项目的建设目标细化为一个总目标与五个分项目标：

**总目标**：在60日历天开发期内，建成覆盖四端、承载三类租赁业态、贯通八大业务域的房屋管理系统，完成存量数据迁移与八项外部系统对接，通过验收后提供6年免费驻场运维服务，支撑港区房屋租赁业务长期稳定运行。

| 分项目标 | 目标描述 | 衡量标准 |
|---|---|---|
| 业务全流程线上化 | 选房、签约、入住、退租、续租、缴费、开票等核心业务全部线上办理 | 211项功能明细全部实现并通过验收 |
| 资格核验自动化 | 保租房、人才公寓资格通过政务数据接口自动核验 | 社保/婚姻/学历/住房/保租房五维自动校验上线，人工审核兜底 |
| 多端体验一致化 | 移动端、小程序端、公众号端功能与体验完全一致 | 三端功能项覆盖率100%，同一业务多端办理结果一致 |
| 数据资产完整化 | 存量业务数据完整迁移，经营数据实时可视 | 迁移数据比对一致率100%，数据看板核心指标实时更新 |
| 运行保障长效化 | 建立驻场运维体系，保障系统长期稳定 | 年可用率≥99.5%，紧急故障10分钟响应，免费运维6年 |

## 1.3 项目建设重难点解析

结合我方在同类保障性住房租赁管理平台建设中的实践经验，我们对本项目的重难点解析如下：

### 1.3.1 重点一：三类业态统一承载与差异化流程设计

人才公寓、保租房、市场租赁三类业务的主体流程同构（选房→签约→入住→退租→续租→缴费→开票），但在**资格校验规则**（人才公寓需人才认定，保租房需社保/婚姻/学历/住房多维核验，市场租赁仅查欠费）、**配租方式**（常规分配/集中分配/企业集中配租）、**审批链路**上存在显著差异。

**应对策略**：采用"统一业务模型 + 业务类型策略分流"的设计模式，合同、账单、房源使用统一数据模型并以业务类型字段区分，资格校验、续租校验等差异化环节采用策略模式按业务类型分流处理，既保证代码复用降低维护成本，又支持各业态规则独立演进。

### 1.3.2 重点二：多渠道政务数据对接与自动资格核验

保租房资格自动校验需要对接社保、婚姻、学历、住房、保租房共5类政务数据接口，接口分属不同层级（郑州市级/港区级），存在网络环境隔离、接口协议差异、响应时效不稳定等问题。

**应对策略**：我方在同类项目中已完整实现政务数据接口对接，采用"**政务接口代理网关**"模式：由部署于可访问政务网络环境的代理服务统一封装各政务接口，业务系统仅与代理网关交互；核验结果按业务规则设置合理缓存周期，减少重复调用；接口异常时自动降级为"人工审核"通道并给用户明确提示，保证业务不中断。该模式已在生产环境稳定运行，可低成本复用至本项目。

### 1.3.3 重点三：支付资金安全与账单准确性

押金、租金在线支付涉及资金安全，需处理支付回调丢失、重复支付、超时未支付、部分退款等复杂场景；账单生成需精确处理租期拆分、优惠券抵扣、逾期计算等规则，"押金未缴不可选租期账单缴费"等业务约束必须严格保证。

**应对策略**：基于我方成熟的支付对接经验，实施"**支付状态机 + 回调兜底 + 主动对账**"三重保障：订单状态机严格约束状态流转，防止重复支付；支付回调幂等处理，并以定时任务主动查询支付渠道补偿回调丢失；超时未支付订单自动取消释放房源；退款按账单明细拆分执行；每日与支付渠道对账，差异及时告警人工介入。

### 1.3.4 重点四：存量数据迁移的完整性与业务连续性

现有系统承载着在租合同、在途账单、历史缴费等生产数据，迁移过程必须保证数据不丢、不错、不重，且新旧系统切换期间业务不中断。

**应对策略**：我方具备同类系统老数据迁移的完整实战经验，采用"**分域清洗—映射转换—试迁移校验—增量补迁—并行核对**"五步迁移法：先对房屋、用户、合同、账单四大数据域分别制定清洗规则与字段映射表；在测试环境完成试迁移并输出比对报告（记录数、金额合计、关键字段抽样比对）；正式切换选择业务低峰期，切换后保留旧系统只读查询一段时间，用于并行核对与追溯。

### 1.3.5 重点五：多端一致性与低成本维护

移动端、小程序端、公众号端功能要求完全一致，若各端独立开发将造成约三倍的开发与维护成本，且极易出现多端行为不一致。

**应对策略**：采用 **uni-app 跨端统一开发框架**，一套代码编译产出 H5、微信小程序、公众号（H5内嵌）三端应用，业务逻辑、接口调用、页面交互完全一致；仅对人脸识别等平台差异能力做条件编译适配。该方案可显著压缩开发工期，并保证后续需求迭代"一处修改、三端生效"。

### 1.3.6 难点：驻场开发模式下的进度与质量双控

本项目开发期仅60日历天、总人月数不少于37人月，工期紧、任务重，且驻场开发需与甲方深度协同，需求确认、联调对接、验收节奏都依赖高效的协作机制。

**应对策略**：详见本方案第三章项目实施管理与第六章服务期限保证。核心措施包括：进场即冻结需求基线、按周迭代交付可视化成果、每日站会+每周例会双频同步、里程碑评审制、关键路径（政务接口/支付/电子签章对接）提前启动联调申请。

## 1.4 项目业务需求分析

### 1.4.1 业务角色分析

### 1.4.2 核心业务流程需求

#### 1.4.2.1 资格申诉与核验流程

系统自动调用政务接口核验资格，不符项支持用户手动刷新与在线申诉，管理端人工复核，形成"自动核验为主、人工审核兜底"的资格管理闭环。

| 环节 | 参与角色 | 流程要求 |
|---|---|---|
| 自动核验 | 系统 | 用户发起申请后，自动调用社保（郑州市）、婚姻（郑州市）、学历（郑州市）、住房（港区）、保租房（港区）核验接口，逐项返回核验结果 |
| 不符项展示 | 租户 | 核验不通过项以列表形式明确展示，注明不符原因 |
| 手动刷新 | 租户 | 用户补正信息后（如社保补缴到账）可手动触发重新核验 |
| 在线申诉 | 租户 | 对核验结果有异议的，在线提交申诉说明与佐证材料 |
| 人工复核 | 运营管理人员 | 管理端受理申诉，人工审核后录入复核结论，结论回写资格状态 |
| 记录留痕 | 系统 | 每次核验、申诉、复核均留存记录，支持导出审计 |

#### 1.4.2.2 选房签约流程

项目/房源浏览（含VR看房、地图导航）→ 签订承诺书 → 选定房源 →（人脸识别核验）→ 在线签署合同（电子签章）→ 押金缴纳（限时上传材料，超时自动退押解约）。流程关键需求点：

- 房源列表须按楼栋/单元/房间层级展示，支持户型、朝向、楼层等条件筛选；
- 房源详情提供照片、公示信息、周边配套、VR看房、地图导航、管家电话，信息充分辅助决策；
- 选房前须在线签订承诺书；小程序/公众号端签约前进行人脸识别，核验签约人与选房人一致；
- 合同采用电子签章在线签署，签署完成支持在线下载；
- 押金缴纳设置时限，同时限时上传要求材料，超时系统自动退还押金并取消合同、释放房源。

#### 1.4.2.3 入住办理流程

入住申请 → 管理端签收审核 → 租户勾选房间物品核对状态 → 电子签字确认入住。要求物品核对清单由系统按房源设施配置自动生成，租户逐项勾选核对，签字确认后形成入住确认单存档；企业客户支持上传入住人员名单模板批量办理。

#### 1.4.2.4 居住服务流程

投诉建议、保洁/搬家/报修订单在线申请，管理端分派服务公司，租户在线评价。要求服务订单全程状态可查（已申请/已分派/服务中/已完成/已评价），服务公司作为独立管理对象支持增删改查与服务范围配置。

#### 1.4.2.5 退租结算流程

退租申请 → 管理端签收 → 物品核对与退费信息确认 → 电子签字确认退租 → 退款申请、审批、退费。要求退费金额由系统按租期自动计算并支持人工调整留痕；退款须经审批流程，审批通过后原路退回；管理端另需支持强制退租处理能力。

#### 1.4.2.6 续租管理流程

续租资格校验（人才公寓/保租房校验资格+欠费，市场租赁仅校验欠费）→ 续租合同在线签订 → 管理端审批 → 租金缴纳提示。要求续租校验规则按业态差异化配置，校验不通过时明确提示不通过原因。

#### 1.4.2.7 账单缴费与开票流程

账单自动生成 → 在线支付（支持优惠券抵扣）→ 逾期催缴 → 按账期申请开票 → 发票在线预览下载。关键约束：**押金账单未缴清前不允许选择租期账单缴费**；支付对接港区支付接口，支持第三方在线支付；优惠券抵扣金额自动计算；管理端支持按账单维度催缴并记录催缴历史。

#### 1.4.2.8 运营管理流程

配租批次管理（新增/编辑/作废/审批/详情）、企业客户集中配租、黑名单管理、金刚位/轮播图/腰封位/广告位运营配置、通知公告与政策文件发布。要求集中配租支持房源与人员的批量绑定与审批流转，运营位配置实时生效。

### 1.4.4 需求理解的三个关键判断

基于对招标需求的整体分析，我方形成以下三个关键判断，并以此指导方案设计：

1. **本项目是"业务平台"而非"信息展示系统"**：211项功能中约80%涉及业务流转、状态变更与资金往来，系统设计必须以业务状态机、审批流、资金安全为核心，而非简单的信息增删改查；
2. **对接质量决定项目成败**：郑好办、政务核验、支付、签章、人脸识别、地图、监控、公共数据8类对接贯穿核心流程，任何一个对接不畅都会阻断主业务链路，因此对接工作必须提前启动、并行推进、预设降级方案；
3. **迁移与并行期是风险最集中的阶段**：存量在租合同与在途账单迁移后必须立即可用，切换期间的每一笔缴费都不能出错，必须以演练充分、可回退的迁移方案保障平稳过渡。

**（4）合同与业务管理**：合同管理覆盖常态化合同与集中合同（查询/导出/续租审批）；入住管理区分常态入住（签收/作废/强制退租）与企业入住；退租管理支持物品核对与退费确认；退款管理走申请/撤销/审批/退费闭环；合住人与调换房走审批流；租金账单支持查询/催缴/导出/详情；代购补贴含合同备案审批与补贴申请审批。本模块是运营人员日常使用频率最高的业务中枢，审批时效与操作留痕是核心要求。

**（6）报表与运营管理**：报表管理（项目收款台账/自定义报表）、优惠券管理（管理/领取记录/核销明细）、黑名单管理、用户管理、配置管理（消息通知模板、合同模板——付款周期/签约期限/押金金额、运营配置——金刚位/轮播图/腰封位/广告位、通知公告、政策文件）。其中**自定义报表**要求支持运营人员自选统计维度与字段生成报表并导出；**合同模板配置**直接决定签约业务规则，变更须有审批与生效控制。

**（7）系统管理**：用户/账号/角色/权限（菜单权限+数据权限）/字典/消息管理（渠道+队列）/安全日志（登录日志、操作日志可查可追溯），为全系统提供统一的权限与配置底座。

### 1.5.3 实施与对接需求

数据迁移（房屋/合同/账单/用户数据）、系统使用培训、公共数据接口对接（房管局/不动产权中心）、地图对接、资格核验接口对接、监控对接、支付渠道对接、电子签章对接、公众号端与小程序端构建、人脸识别调用，共11项。

### 1.5.4 功能需求理解小结

我方已逐项研读全部211项功能明细，并与我方已建成运行的同类住房租赁管理平台功能体系进行了逐项比对：**约90%的功能项与我方已有成熟实现直接对应**（选房签约、入住退租、账单支付、开票、配租批次、企业集中配租、服务订单、数据看板等），其余功能项（优惠券核销体系、自定义报表、监控对接等）我方已有清晰的技术实现路径。这使我方能够以"成熟方案定制化适配"取代"从零开发"，在60日历天开发期内高质量完成交付。

3. **防错设计**：关键操作二次确认、表单实时校验即时提示、超时操作自动保存草稿；

### 1.6.5 可扩展性与可维护性需求

1. **业务可扩展**：业务类型策略化设计，新增业态（如新增配租政策类型）仅需扩展策略实现而不改动主干代码；

5. **文档与注释**：交付代码注释完整、文档齐套，保障甲方后续自主维护与二次开发。

系统需满足网络安全等级保护二级要求，遵循《网络安全法》《数据安全法》《个人信息保护法》相关规定：身份鉴别、访问控制、安全审计、数据加密、个人信息最小化采集与脱敏展示、日志留存不少于6个月。详细安全设计见本方案第四章。

| 关键业务规则 | 该功能必须满足的约束条件、校验规则、状态联动 |

所有功能点的数据操作均遵守统一的通用设计约定，不在逐项表中重复描述：

1. **权限约定**：管理端每个功能均受RBAC权限控制（菜单可见性、按钮操作权、数据范围权三级）；用户端功能均需登录后访问（政策浏览类除外）；
2. **留痕约定**：所有新增、修改、删除、审批、导出操作均记录操作日志（操作人、时间、对象、内容摘要）；
3. **列表约定**：管理端列表页均支持多条件组合查询、分页、排序；带导出功能的列表导出字段与查询结果一致；
4. **表单约定**：所有表单前后端双重校验，必填项、格式、长度、数值范围校验规则一致；
5. **状态约定**：涉及状态流转的业务对象（房源、合同、账单、订单、审批单）均采用状态机管理，非法状态跳转一律拒绝并留痕。

### 2.5.1 房源管理

**设计概述**：房源管理是全系统的资产数据底座，建立"项目→楼栋→单元→房源"四级资产台账，向上支撑选房、签约、入住业务，向下联动数据看板的出租率统计。设计目标：资产账实一致、房源状态与业务实时联动、配租方式灵活可配。

| 功能点 | 功能设计说明 | 关键业务规则 |

| 企业客户集中配租 | 面向企业客户的批量配租：企业信息+集中分配房源清单绑定，企业端在线缴费、批量入住 | 企业配租房源不进入个人选房池；企业欠费时限制新增配租 |
| 预约看房管理 | 用户端在线预约看房，管理端签收/确认预约并安排带看 | 同一用户对同一项目的有效预约不重复创建；预约状态变化触发消息通知 |

### 2.5.2 合同管理

**设计概述**：合同管理承载租赁关系的法律载体，覆盖"模板配置→在线签署→履行管理→续租/变更→到期/解除"全生命周期，对接电子签章保证合同法律效力。设计目标：签署流程合规可信、合同状态自动管控、多类型合同统一台账。

| 功能点 | 功能设计说明 | 关键业务规则 |
|---|---|---|
| 合同模板配置 | 管理端按项目/业态配置合同模板：付款周期（月付/季付/半年付/年付）、签约期限、押金金额等签约要素；模板版本化管理 | 模板变更仅影响新签合同，存量合同按签署时模板执行；模板要素变更留痕可追溯 |
| 合同在线签署 | 租户在线阅读合同全文→确认签约信息→电子签名→平台与租户双方签章→合同生成PDF存证；支持合同在线下载 | 签署前完成人脸识别核验（小程序/公众号端）；签署链接限时有效；签署完成不可篡改 |
| 合同状态管理 | 待签署、待生效、履行中、待续签、已到期、已解除、已作废全状态机管理；定时任务自动处理到期提醒、超时未签作废、押金超时解约 | 状态流转均有触发条件与留痕；解除/作废须记录原因；状态变化联动房源状态与账单停止生成 |
| 续租办理 | 用户端发起续租→系统校验（人才公寓/保租房：资格+欠费；市场租赁：仅欠费）→在线签署续租合同→管理端续租审批→租金缴纳提示 | 续租合同租期与原合同无缝衔接；校验不通过明确提示原因；原合同到期前设置续租提醒窗口 |
| 合同台账 | 常态化合同与集中合同统一台账：多条件查询（项目/业态/状态/租期/租户）、导出、详情追溯（签署记录/账单记录/变更记录） | 导出受权限控制并留痕；集中合同关联配租批次信息 |
| 我的合同（用户端） | 合同列表与详情：合同要素、签署状态、关联账单入口、续租入口、合同下载 | 市场租赁新签约合同展示签约倒计时；仅本人合同可见 |
| 合同备案（代购补贴） | 用户端发起合同备案（上传备案材料）→管理端备案审批→备案进度查询 | 备案通过方可发起代购补贴申请；审批意见回传用户端 |
| 合住人管理 | 用户端提交合住人申请（合住人身份信息）→管理端审批→合住人信息关联合同 | 合住人数量受房型限制；合住人身份信息脱敏展示 |

### 2.5.3 支付管理

**设计概述**：支付管理是资金往来的核心域，覆盖"账单生成→在线支付→对账→退款→催缴→开票"完整资金链路，对接港区支付接口。设计目标：账单准确、资金安全、每一分钱可对账可追溯。

逐项功能设计如下：

| 功能点 | 功能设计说明 | 关键业务规则 |
|---|---|---|
| 押金账单 | 合同签署后自动生成押金账单，用户端在线缴纳；押金缴纳设时限并联动材料上传要求 | 超时未缴自动退押金、取消合同、释放房源；押金金额取自合同模板配置 |
| 租金账单 | 按合同付款周期自动拆分生成租期账单（账期起止、应缴金额、缴费截止日）；支持账单详情查看 | **押金账单未缴清前，租期账单不可选择缴费**；账期拆分精确到日，首末期按天数折算 |
| 在线支付 | 对接港区支付接口发起第三方在线支付：下单→跳转支付→回调确认→账单核销；支持优惠券抵扣计算 | 支付订单状态机严格管理（待支付/支付中/已支付/已关闭/已退款）；回调验签+幂等处理；超时订单自动关闭 |
| 优惠计算 | 缴费时自动匹配用户可用优惠券，计算抵扣金额并展示实付金额 | 优惠券使用规则（适用范围/有效期/面额）严格校验；一笔账单限用规则可配置；核销记录留痕 |
| 主动对账 | 每日定时与支付渠道对账单比对：平台订单与渠道流水逐笔核对，差异生成对账异常清单 | 差异账单冻结自动核销，人工处理后闭环；对账结果日报留存 |
| 退款管理 | 退租结算/超时退押场景发起退款申请→（撤销）→管理端审批→调用渠道退款→退款结果确认→凭证留存 | 退款按原账单明细拆分执行、原路退回；退款单与原支付单强关联；审批留痕 |
| 账单催缴 | 逾期账单自动标记，管理端支持单笔/批量催缴，触发消息通知（站内信/模板消息/短信可配置）；催缴历史记录 | 逾期规则（宽限期）可配置；催缴频次受限防骚扰 |
| 项目收款台账 | 按项目/按月统计应收、实收、逾期、退款，支持导出 | 台账口径与账单明细严格一致，支持追溯到单笔账单 |
| 开票管理 | 用户端按账期申请开票（选择已缴账期）→管理端受理并上传发票文件→用户端发票预览与下载；开票记录全程可查 | 同一账期不可重复申请开票；发票文件与账单关联存档 |
| 企业在线缴费 | 企业客户对集中分配房源批量缴费：企业信息+房源清单+账期汇总缴纳 | 企业缴费生成汇总支付单，核销时拆分回写各房源账单 |

**资金安全三重保障机制**：

1. **支付状态机**：订单状态流转严格受控，同一账单不允许并发生成多个有效支付单，从源头防止重复支付；
2. **回调兜底**：支付回调幂等处理（同一回调多次到达仅生效一次）；定时任务主动查询支付渠道订单状态，补偿回调丢失场景，确保"渠道已扣款、平台未核销"的账单最终一致；
3. **每日对账**：以渠道对账单为基准逐笔核对，差异当日告警、专人处理、处理结果留痕，实现资金零差错闭环。

### 2.5.8 数据看板

**设计概述**：数据看板面向管理决策层与财务，将业务过程数据加工为实时经营指标。设计目标：指标准确一致、维度灵活下钻、报表自助可得。

**指标一致性设计**：所有看板指标统一由指标计算服务提供，明细—汇总同源计算，杜绝"看板一个数、报表另一个数"；统计类查询走只读从库与缓存，不影响在线交易性能。

## 2.6 系统接口设计

### 2.6.1 接口设计原则

统一采用 RESTful 风格 + JSON 报文；接口全部纳入 OpenAPI 3.0 在线文档；外部接口一律通过适配器层封装，做到"外部协议变化不侵入业务代码"；所有接口调用记录日志（请求方、时间、参数摘要、结果、耗时），可查可追溯。

### 2.6.2 郑好办用户体系对接

采用 OAuth2 授权模式对接郑好办统一用户体系：用户在移动端发起登录→跳转郑好办授权→回调携带授权码→后端换取访问令牌→获取用户身份信息→本地建立/关联用户档案→颁发系统 JWT 会话。令牌获取采用双重检查锁+Redis 缓存机制，避免并发重复请求；令牌到期自动刷新。对接时序如下图所示：

![图2-6 郑好办用户体系对接时序图](images/08-郑好办对接时序图.png)

郑好办对接接口逐项定义如下：

| 接口 | 方向 | 触发场景 | 关键请求要素 | 关键响应要素 | 异常处理 |
|---|---|---|---|---|---|
| 授权跳转 | 本系统→郑好办 | 用户点击登录 | 应用标识、回调地址、状态码 | 授权页跳转 | 跳转失败提示重试，记录失败日志 |

### 2.6.3 政务数据资格核验对接

通过政务接口代理网关对接社保（郑州市）、婚姻（郑州市）、学历（郑州市）、住房（港区）、保租房（港区）5类核验接口以及房管局、不动产权中心公共数据接口：

- 代理网关部署于可访问政务网络的环境，统一鉴权、统一报文转换、统一日志留痕；
- 核验结果结构化落库并缓存，支持用户手动刷新重新核验；
- 接口不可用时自动降级人工审核通道，业务不中断；
- 敏感个人信息按最小必要原则调用，传输全程加密。

资格核验接口逐项定义如下：

| 接口 | 数据层级 | 核验内容 | 调用时机 | 结果处理 | 降级策略 |
|---|---|---|---|---|---|
| 社保信息核验 | 郑州市级 | 参保状态、缴费单位、连续缴费情况 | 资格校验发起/用户手动刷新 | 结构化落库，比对准入规则输出符合/不符合项 | 接口超时重试2次后转人工审核 |
| 婚姻信息核验 | 郑州市级 | 婚姻登记状态 | 同上 | 同上 | 同上 |
| 学历信息核验 | 郑州市级 | 最高学历、毕业院校 | 同上 | 同上 | 同上 |
| 住房信息核验 | 港区级 | 本区自有住房情况 | 同上 | 同上 | 同上 |
| 保租房信息核验 | 港区级 | 是否已承租保租房 | 同上 | 同上 | 同上 |
| 房管局公共数据 | 市/区级 | 房屋登记相关信息 | 业务按需调用 | 结果留痕 | 人工核查兜底 |

**核验结果缓存与刷新机制**：核验结果设置有效期缓存，有效期内重复校验直接返回缓存结果不再调用政务接口，降低政务接口压力；用户点击"手动刷新"强制穿透缓存重新调用；每次核验的调用时间、数据来源、比对结论完整留痕，支撑资格审核的事后追溯。

### 2.6.5 内部接口与数据交换

前后端接口统一网关入口、统一响应结构（代码/消息/数据三段式）、统一异常处理；批量数据交换（房源导入、租户导出、迁移数据）采用模板化 Excel + 异步任务 + 结果回执模式，保证大批量数据处理不阻塞在线业务。

**接口规范细则**：

1. **命名规范**：URL 按"/模块/资源/动作"层级组织，资源名用名词复数，动作语义由 HTTP 方法表达（GET查询/POST新增/PUT修改/DELETE删除）；
2. **报文规范**：请求与响应统一 UTF-8 编码 JSON 报文；时间格式统一 yyyy-MM-dd HH:mm:ss；金额统一以分为单位的整数传输，杜绝浮点精度问题；
3. **分页规范**：列表接口统一 pageNum/pageSize 入参与 total/rows 出参结构；
4. **鉴权规范**：所有业务接口携带 JWT 令牌，网关统一校验；开放回调类接口采用签名验签+IP白名单双重防护；
5. **幂等规范**：所有写操作接口支持幂等（业务唯一键约束或幂等令牌），防止网络重试导致的重复提交；
6. **版本规范**：接口版本化管理，新版本上线保持旧版本兼容过渡期，避免多端发版不同步导致的接口不可用。

### 2.6.6 接口异常处理与容错设计

针对外部接口不可用、超时、返回异常三类故障场景，统一容错设计如下：

| 外部接口 | 故障场景 | 容错策略 | 用户侧体验 |
|---|---|---|---|
| 郑好办认证 | 授权服务不可用 | 已登录会话不受影响；新登录友好提示稍后重试 | 明确的错误提示与重试入口 |
| 政务核验 | 超时/不可用 | 重试2次→自动降级人工审核通道 | 提示"已转人工审核"，业务不中断 |
| 支付渠道 | 回调丢失 | 定时任务主动查单补偿，保证最终一致 | 支付结果页轮询，短暂延迟后正确显示 |
| 支付渠道 | 下单失败 | 幂等重试；持续失败则账单保持待缴状态 | 提示重试，账单状态不错乱 |
| 电子签章 | 签署流异常 | 回调+回查双通道；超时作废可重新发起 | 签署状态透明，可重新发起 |
| 人脸识别 | 识别服务异常 | 有限次重试；持续失败转人工核验通道 | 提示改用人工核验，流程可继续 |
| 地图服务 | 加载失败 | 前端降级为列表模式 | 找房功能不中断 |
| 园区监控 | 视频源中断 | 管理端标注离线状态，恢复自动重连 | 不影响其他业务 |

**熔断与隔离**：外部接口调用统一设置超时（连接/读取分离配置）与熔断阈值，故障接口快速失败不拖垮主线程池；各外部依赖独立线程池隔离，单一外部故障不产生雪崩效应。所有异常调用记录接口日志并触发告警，供运维快速定位。

3. **金额规范**：金额字段以分为单位整型存储，展示层格式化，从存储层杜绝小数精度差错；
4. **索引规范**：高频查询条件建立复合索引；大表（账单、日志、消息）按时间维度规划归档策略；
5. **敏感数据规范**：证件号、手机号等敏感字段加密存储、脱敏展示，密钥独立管理。

## 2.8 系统安全设计

系统安全设计贯穿身份认证（郑好办统一认证+JWT+会话管理）、访问控制（RBAC菜单/按钮/数据三级权限）、传输安全（全站HTTPS）、数据安全（敏感字段加密存储、脱敏展示）、应用安全（SQL注入/XSS/CSRF防护、接口签名与幂等）、审计安全（登录/操作/接口日志全留痕）六个层面，整体按照网络安全等级保护二级标准设计建设。详细安全解决方案见本方案第四章"系统安全管理"。

应用层关键场景的安全设计要点如下：

| 安全场景 | 威胁 | 设计措施 |
|---|---|---|
| 登录认证 | 凭证窃取、会话劫持 | 郑好办统一认证，本系统不存密码；JWT短有效期+刷新机制；同账号异常登录检测 |
| 越权访问 | 水平/垂直越权 | 接口级鉴权+数据行级权限双重校验；用户端接口强制校验数据归属（仅本人合同/账单可见） |
| 支付安全 | 金额篡改、重复支付、伪造回调 | 金额以服务端账单为准不信任前端；订单状态机+幂等；回调验签+IP白名单 |
| 文件上传 | WebShell、带毒文件 | 类型白名单+内容检测+重命名+隔离存储+禁执行权限 |
| 敏感数据 | 泄露、滥用 | 证件号/手机号加密存储、界面脱敏；导出脱敏与权限控制；最小必要采集 |
| 接口滥用 | 爬取、刷单、短信轰炸 | 限流、验证码、频次控制；关键操作行为日志分析告警 |
| 前端安全 | XSS、CSRF | 输入输出双向过滤转义、CSP策略、Token校验、敏感操作二次确认 |

### 3.5.1 编码规范细则（要点）

| 类别 | 规范要点 |
|---|---|
| 命名 | 类名大驼峰、方法/变量小驼峰、常量全大写下划线；包名按"公司.项目.模块.分层"组织；禁止拼音缩写混用 |
| 分层 | Controller只做参数校验与结果封装，业务逻辑收敛Service层，数据访问收敛Mapper层；禁止跨层调用 |
| 异常 | 统一业务异常体系，全局异常处理器兜底；禁止吞异常、禁止捕获后仅打印不处理 |
| 事务 | 事务边界在Service层声明；跨服务数据一致性采用补偿/对账机制；长事务拆分 |
| 日志 | 统一日志门面；关键业务动作INFO级留痕；敏感字段（证件号/手机号）日志脱敏；禁止System.out |
| 注释 | 类/公共方法必须有文档注释；复杂业务逻辑行内注释说明"为什么"；源代码交付注释完整可读 |
| 前端 | 组件化开发、公共组件下沉；接口调用统一封装；页面状态与接口异常统一处理；禁止硬编码接口地址 |

| 类别 | 规范要点 |
|---|---|

## 3.7 低成本、标准化实现系统互联互通

我方以"标准优先、复用优先、配置优先"三原则实现系统互联互通的低成本落地：

1. **标准化接口体系**：全部对外/对内接口采用 RESTful + JSON 统一标准，OpenAPI 3.0 文档自动生成，第三方接入无需定制开发即可完成联调，降低双方对接成本；
2. **适配器模式隔离外部差异**：支付、签章、人脸、地图、监控等外部能力均以适配器封装，更换服务商仅需替换适配器实现，业务代码零改动，避免供应商锁定带来的重复建设成本；
3. **政务接口代理网关复用**：我方已建成并在生产环境稳定运行的政务数据代理网关（统一鉴权、报文转换、缓存、降级、日志），可直接复用于本项目的资格核验与公共数据对接，节省该部分从零开发成本；
4. **成熟平台底座复用**：统一权限、字典、日志、代码生成、任务调度等平台能力为我方成熟资产，直接复用，将人力集中投入业务功能开发；
5. **模板化数据交换**：批量导入导出、数据迁移采用标准 Excel 模板 + 校验回执机制，与甲方既有办公习惯无缝衔接，无需额外采购数据交换工具。

**可复用标准能力清单**：

| 能力项 | 复用来源 | 复用方式 | 节省工作量估算 |
|---|---|---|---|
| 政务接口代理网关 | 我方生产运行资产 | 直接部署+参数适配 | 约1.5人月 |

## 4.1 系统漏洞风险防控

### 4.1.1 开发阶段漏洞预防

- **安全编码规范**：强制执行输入校验、输出编码、参数化查询（MyBatis-Plus 预编译杜绝SQL拼接）、文件上传白名单校验（类型/大小/重命名存储）、反序列化限制等安全编码要求；
- **框架级防护**：Spring Security 统一认证鉴权，接口默认拒绝匿名访问；全局 XSS 过滤器对请求参数净化；CSRF 防护与同源校验；
- **依赖组件治理**：建立第三方组件清单，版本纳入配置管理；上线前执行依赖漏洞扫描，高危组件（如存在已公开CVE）强制升级或替换；
- **代码安全审计**：静态代码扫描纳入CI流水线，安全类缺陷阻断合并；核心模块（认证、支付、资格核验）人工安全评审。

### 4.1.2 运行阶段漏洞管理

- **漏洞扫描**：系统上线前及运行期定期（每季度）开展主机漏洞扫描与Web应用漏洞扫描，输出扫描报告；
- **渗透测试**：上线前配合甲方或第三方机构开展渗透测试，问题限期整改复测；
- **补丁管理**：操作系统、中间件、数据库补丁评估—测试环境验证—生产窗口期更新的三步流程，重大安全补丁48小时内完成评估；
- **漏洞响应**：收到漏洞通报（甲方、监管、CNVD等渠道）后，高危漏洞24小时内完成处置或临时缓解措施。

### 4.1.3 安全基线配置规范

我方为生产环境各组件制定安全基线，部署时逐项核对、运行期定期复查：

**操作系统基线（Linux）**：

| 基线项 | 配置要求 |
|---|---|
| 账号策略 | 禁用直接root远程登录；运维账号实名；口令复杂度与有效期策略生效 |
| 服务最小化 | 关闭无关系统服务；卸载无关软件包；仅开放业务必需端口 |
| SSH加固 | 修改默认端口、密钥登录优先、失败锁定、登录超时 |
| 审计配置 | 开启系统审计（auditd），记录特权命令与关键文件变更 |
| 内核参数 | 关闭ICMP重定向、开启SYN Cookie等防护参数 |

**中间件基线（Nginx）**：

| 基线项 | 配置要求 |
|---|---|
| 版本信息隐藏 | 关闭版本号回显（server_tokens off） |
| TLS配置 | 仅启用TLS 1.2+，禁用弱加密套件 |
| 限流防护 | 连接数限制、请求速率限制、请求体大小限制 |
| 安全响应头 | X-Frame-Options、X-Content-Type-Options、CSP等安全头统一下发 |
| 目录防护 | 禁止目录浏览；上传目录禁止执行脚本 |

**数据库基线（MySQL）**：

| 基线项 | 配置要求 |
|---|---|
| 网络访问 | 仅监听内网地址，仅授权应用服务器网段访问 |
| 账号分权 | 应用/运维/备份/只读账号分离，禁用匿名账号，应用账号无DDL权限 |
| 口令策略 | 强口令、定期更换、禁止硬编码明文（配置加密存储） |
| 日志审计 | 开启慢查询日志、错误日志；关键库表变更留痕 |
| 备份加密 | 备份文件加密存储、异机存放、权限受控 |

**缓存基线（Redis）**：

| 基线项 | 配置要求 |
|---|---|
| 访问控制 | 仅内网监听、启用密码认证、禁用危险命令（FLUSHALL/CONFIG等重命名） |
| 数据安全 | 不存储明文敏感数据；键设置合理过期时间 |

**应用基线（Spring Boot）**：

| 基线项 | 配置要求 |
|---|---|
| 配置安全 | 生产配置与代码分离，数据库口令、接口密钥加密存放 |
| 接口安全 | actuator等管理端点关闭或鉴权保护；Swagger生产环境关闭 |
| 错误处理 | 统一异常处理，生产环境不回显堆栈信息 |
| 日志安全 | 敏感字段输出统一脱敏；日志级别生产环境为INFO及以上 |

## 4.2 病毒风险防控

- **服务器侧**：生产服务器安装防病毒软件并保持病毒库自动更新，定期全盘查杀；最小化安装原则关闭无关服务与端口，禁用未授权外设与移动介质；
- **应用侧**：文件上传统一经过类型白名单校验、内容检测与重命名隔离存储，上传目录禁止执行权限，从源头阻断WebShell与带毒文件；
- **终端侧**：驻场开发终端统一安装防病毒软件，接入甲方网络前完成安全检查，遵守甲方终端管理规定；
- **传播阻断**：网络分区隔离（见4.3），关键服务器间仅开放必要端口，病毒即使侵入也难以横向扩散。

**防病毒部署矩阵**：

| 部署对象 | 防护措施 | 病毒库更新 | 查杀策略 |
|---|---|---|---|
| 应用服务器 | 服务器防病毒软件+最小化安装+端口白名单 | 每日自动更新 | 每周全盘查杀，日志留存 |
| 数据库服务器 | 防病毒软件（排除数据文件目录防误杀）+访问白名单 | 每日自动更新 | 每周全盘查杀（业务低峰执行） |
| 文件存储目录 | 上传文件类型白名单+内容检测+重命名隔离+禁执行权限 | — | 上传即检、定期复扫 |
| 驻场办公终端 | 统一防病毒软件+补丁管理+移动介质管控 | 每日自动更新 | 每周查杀+接入前检查 |

**病毒安全事件处置流程**：发现（告警/巡检）→ 隔离（受染主机断网或访问隔离）→ 查杀（专杀工具处置，无法清除则重装）→ 溯源（感染途径分析，堵住入口）→ 恢复（业务验证后恢复接入）→ 报告（2小时内向甲方报告事件与处置结果，形成事件报告归档）。全程处置动作留痕，重大病毒事件按应急预案（见第五章）升级处置。

**日常管理要求**：每周巡检核查各节点病毒库版本与查杀日志；禁止在生产服务器安装与运行无关软件；外来文件（含甲方提供的数据文件）先查毒后使用；病毒防控执行情况纳入月度安全运营报告。

## 4.3 黑客攻击风险防控

系统构建"网络边界—应用—数据"三层纵深防御体系，如下图所示：

![图4-2 纵深防御体系图](images/30-纵深防御体系图.png)

### 4.3.1 网络边界防护

- **防火墙策略**：边界防火墙白名单策略，仅开放业务必需端口（443等）；管理端口（SSH、数据库）禁止公网暴露，仅限运维专用通道访问；
- **网络分区**：按"接入区—应用区—数据区"划分安全域（VLAN隔离），数据库仅接受应用服务器网段访问；
- **DDoS与流量防护**：接入层限流（Nginx 连接数/请求速率限制），异常流量告警，必要时联动上游清洗服务；
- **传输加密**：全站 HTTPS（TLS 1.2+），证书规范管理，杜绝明文传输。

### 4.3.2 应用层攻击防护

- **认证安全**：登录失败次数限制与账户锁定、验证码机制、JWT 令牌签名校验与有效期控制、会话超时自动登出、同账号异地登录检测；
- **接口安全**：接口鉴权全覆盖（横向越权校验到数据行级）、支付/签约等敏感接口幂等与防重放（时间戳+随机数+签名）、第三方回调验签；
- **暴力破解防护**：管理端登录接口速率限制，弱口令策略强制（长度、复杂度、定期更换）；
- **入侵检测与审计**：登录日志、操作日志、接口调用日志全量留存（保存期不少于6个月），异常行为（高频失败登录、异常时段操作、批量导出）告警。

### 4.3.3 数据安全防护

- **加密存储**：身份证号等敏感字段加密存储，口令加盐哈希，密钥独立管理并定期轮换；
- **脱敏展示**：身份证、手机号在前端展示与日志输出中统一脱敏（该规范为我方生产系统既有实践）；
- **权限最小化**：数据库账号按应用/运维/备份分权，禁用超级账号跑业务；管理端数据权限按部门/角色收敛；
- **防泄漏**：批量导出功能权限单独控制并留痕；测试环境使用脱敏数据，禁止生产数据出域。

### 4.3.4 渗透测试与攻防演练

- **上线前渗透测试**：上线前委托内部安全团队按OWASP TOP 10开展渗透测试，覆盖认证绕过、越权访问、注入攻击、文件上传、逻辑漏洞（支付金额篡改、优惠券滥用）等场景，输出渗透测试报告，高危漏洞清零后方可上线；
- **运维期年度渗透测试**：每年度开展1次渗透测试复测，覆盖新增功能与历史修复项回归；
- **攻防演练配合**：积极配合甲方及监管部门组织的网络安全攻防演练（如护网行动），演练期间提高监测等级、专人值守，演练发现问题限期整改闭环；
- **安全应急演练**：每年组织不少于1次安全事件应急演练（模拟WebShell植入、数据库拖库、勒索攻击等场景），检验监测发现、隔离处置、恢复报告全流程有效性，演练报告报送甲方。

## 4.4 管理制度缺陷风险防控

建立与技术措施配套的安全管理制度体系：

| 制度 | 核心内容 |
|---|---|
| 安全责任制度 | 项目经理为安全第一责任人，岗位安全职责书面化，全员签订保密承诺书 |
| 账号权限管理制度 | 账号实名唯一、权限最小化、离岗即回收、特权账号双人管理、权限季度复核 |
| 上线发布管理制度 | 发布申请—审批—窗口期执行—验证—回滚预案，禁止未经审批的生产变更 |
| 数据管理制度 | 数据分级分类、备份与恢复演练、生产数据访问审批、导出留痕 |
| 日志审计制度 | 日志集中留存、定期审计、异常事件溯源分析 |
| 安全教育制度 | 人员进场安全培训、季度安全意识教育、钓鱼与社工防范演练 |
| 第三方管理制度 | 外部接口对接安全评估、供应商访问受控、接口密钥定期轮换 |
| 应急响应制度 | 安全事件分级、响应流程、上报机制、事后复盘（与第五章应急预案衔接） |

八项制度的执行条款如下：

### 4.4.1 安全责任制度（执行条款）

1. 项目经理为项目安全第一责任人，对项目全周期安全工作负总责；架构师兼任安全技术负责人，负责安全设计与技术措施落地；运维工程师为日常安全运行责任人；
2. 各岗位安全职责以《岗位安全职责书》书面明确，人员进场时签署确认；
3. 全体项目人员进场前签订个人保密承诺书，承诺不泄露甲方业务数据、系统资料与个人信息，保密义务在离场后持续有效；
4. 每季度开展安全责任落实情况检查，检查结果与人员考核挂钩；
5. 发生安全责任事故，按"事故原因未查清不放过、责任人未处理不放过、整改措施未落实不放过、相关人员未受教育不放过"原则处理。

### 4.4.2 账号权限管理制度（执行条款）

1. 系统账号（应用、数据库、服务器、中间件）实行实名制，一人一号，禁止共用；
2. 权限按最小必要原则授予：申请—审批—授权—记录四步流程，审批人须为该系统权限归口负责人；
3. 特权账号（数据库管理员、服务器root）实行双人管理：口令分段保管，使用须双人在场并登记《特权操作记录单》；
4. 人员离岗（离职、调岗、项目撤出）当日回收全部账号权限，运维工程师执行、项目经理复核；
5. 每季度开展权限复核：输出账号清单与权限矩阵，逐一确认"账号在用、权限匹配岗位"，冗余权限限期清理；
6. 口令策略：长度与复杂度强制要求、定期更换、禁止默认口令与弱口令，系统层面技术强制。

### 4.4.3 上线发布管理制度（执行条款）

1. 生产变更一律走发布流程：《发布申请单》（变更内容、影响范围、验证方案、回滚方案）→项目经理审批→甲方确认（重大变更）→窗口期执行；
2. 发布窗口原则上安排在业务低峰期；涉及停机的发布提前通知甲方并公告用户；
3. 发布执行采用标准化流水线（自动化部署），发布过程双人操作（一人执行、一人复核）；
4. 发布后执行验证清单（核心流程冒烟测试），验证通过方可宣布发布完成；验证不通过立即执行回滚方案；
5. 紧急缺陷修复可走紧急发布通道：口头报备即可执行，48小时内补齐发布单据；
6. 每次发布输出《版本说明》归档，全年发布记录可审计。

### 4.4.4 数据管理制度（执行条款）

1. 数据分级：按敏感程度将数据分为公开、内部、敏感、重要四级，个人身份信息、资格核验信息、支付信息列为敏感级及以上；
2. 敏感数据访问实行审批制：生产数据查询/修数/导出须提交工单，说明用途、范围、时限，审批通过后在监督下执行并全程留痕；
3. 备份策略：数据库每日全量+binlog增量备份，备份文件异机存储；每季度至少1次恢复演练并输出演练报告；
4. 数据导出：批量导出功能权限单独控制，导出记录（操作人、时间、数据范围、行数）留痕可审计；
5. 测试数据管理：测试环境一律使用脱敏数据，禁止生产数据未脱敏出域；
6. 数据销毁：存储介质报废前执行数据安全擦除；临时数据文件用后即删。

### 4.4.5 日志审计制度（执行条款）

1. 日志范围：登录日志、操作日志、接口调用日志、系统运行日志、安全设备日志全量采集；
2. 日志集中管理：各节点日志统一归集存储，保存期不少于6个月；日志文件权限受控、禁止篡改删除；
3. 定期审计：运维工程师每周开展日志抽查审计（异常登录、越权尝试、批量导出、异常时段操作），每月输出审计报告；
4. 异常处置：审计发现可疑行为立即溯源分析，确认为安全事件的按应急响应制度处置并上报甲方；
5. 日志脱敏：日志输出中的证件号、手机号等敏感字段统一脱敏，防止日志成为泄露源。

### 4.4.6 安全教育制度（执行条款）

1. 进场教育：全员进场时完成安全培训（甲方安全规定、保密要求、安全编码规范、终端安全要求），考核通过方可上岗；
2. 季度教育：每季度组织安全意识教育（近期安全事件案例、钓鱼邮件识别、口令安全、办公区安全）；
3. 专项演练：每年组织钓鱼与社会工程学防范演练，演练结果通报并针对性补课；
4. 新规宣贯：甲方安全管理规定更新时，5个工作日内完成全员宣贯签认。

### 4.4.7 第三方管理制度（执行条款）

1. 对接安全评估：新增外部接口对接前开展安全评估（认证方式、传输加密、数据范围、留痕能力），评估通过方可对接；
2. 密钥管理：与第三方交换的接口密钥、证书专人保管、加密存储，按约定周期或人员变动时轮换；
3. 访问受控：第三方人员确需访问项目环境的，须甲方批准、限定范围与时限、全程陪同与留痕；
4. 供应商变更：第三方服务变更（版本升级、协议调整）须提前评估影响并回归测试后生效。

### 4.4.8 应急响应制度（执行条款）

1. 事件分级：按影响范围与严重程度将安全事件分为重大、较大、一般三级；
2. 响应时限：紧急事件10分钟内响应，一般事件2小时内响应；
3. 处置流程：发现/接报→初步研判定级→先行止损（隔离、封禁、降级）→上报甲方→根因排查→恢复验证→事后复盘报告；
4. 上报机制：重大事件立即电话+书面双通道上报甲方安全归口部门，处置进展持续同步；
5. 复盘改进：每起事件输出复盘报告（时间线、根因、损失评估、整改项），整改项闭环跟踪（详细应急预案见第五章）。

### 4.4.9 制度执行监督与检查机制

制度的价值在于执行。我方建立"自查+互查+专项检查+外部审计"四层监督机制，确保上述八项管理制度不流于纸面：

| 检查层级 | 检查主体 | 频次 | 检查内容 | 结果处理 |
|---|---|---|---|---|
| 日常自查 | 各岗位人员 | 每日 | 本岗位制度执行情况随工作日志自查申报 | 异常事项当日上报直接负责人 |
| 交叉互查 | 项目组内互查 | 每月 | 账号权限、日志完整性、备份有效性、发布记录合规性 | 互查发现问题限期3个工作日整改 |
| 专项检查 | 项目经理+安全负责人 | 每季度 | 按制度逐条对照检查，输出《制度执行检查表》 | 检查结果纳入人员季度考核；重大偏差报公司质量部门 |
| 外部审计配合 | 甲方/第三方审计机构 | 按甲方安排 | 配合等保测评、审计检查，提供全部留痕材料 | 审计意见逐条整改并书面反馈 |

**制度执行检查表（模板摘要）**：检查表按八项制度设置检查项，每项标注"符合/基本符合/不符合"三档结论与证据索引（日志编号、审批单编号、记录表编号），检查人与被检查人双签确认。典型检查项包括：离岗人员账号是否在当日禁用、特权操作是否双人复核留痕、备份恢复演练是否按季度执行并有记录、发布是否均有审批单与回退预案、安全教育是否按计划开展并有签到记录等。

**持续改进闭环**：每季度专项检查后召开制度评审会，对检查中暴露的制度缺陷（条款缺失、职责不清、流程不顺）进行修订，修订版本报甲方备案后发布执行，形成"执行—检查—改进—再执行"的PDCA闭环。

### 4.5.1 安全物理环境

本项目应用部署于甲方指定机房/云平台环境，物理环境控制点主要依托甲方基础设施能力落实，我方负责核对确认并在系统定级备案与测评材料中如实呈现：

| 控制点 | 二级控制要求 | 本项目落实措施 |
|---|---|---|
| 物理访问控制 | 机房出入口有专人值守或电子门禁 | 依托甲方机房门禁体系；我方人员进入机房须甲方审批并登记 |

| 防雷击/防火/防水防潮 | 具备防雷、灭火、防水措施 | 依托甲方机房消防、防雷与环境监控设施，进场核对确认 |
| 温湿度控制 | 温湿度在设备运行允许范围内 | 依托机房精密空调与环境监控，异常纳入监控告警 |
| 电力供应 | 稳压与备用供电 | 依托机房UPS与双路供电；系统层面配合做好异常掉电后的自动恢复与数据一致性校验 |

### 4.5.2 安全通信网络

| 控制点 | 二级控制要求 | 本项目落实措施 |
|---|---|---|
| 网络架构 | 划分网络区域、关键节点冗余 | 按"接入区—应用区—数据区"三区划分（VLAN隔离）；Nginx双节点、应用双实例避免单点 |
| 通信传输 | 采用校验/密码技术保证传输完整性 | 全站HTTPS（TLS 1.2+）；与政务核验、支付、签章等外部接口通信采用签名+加密双重保护 |
| 可信验证 | 对通信设备的系统引导与应用程序进行可信验证 | 服务器操作系统基线加固，关键程序文件完整性定期校验，异常告警 |

### 4.5.3 安全区域边界

| 控制点 | 二级控制要求 | 本项目落实措施 |
|---|---|---|
| 边界防护 | 跨边界访问经受控接口通信 | 互联网流量统一经边界防火墙+Nginx接入层进入，未授权端口一律关闭 |
| 访问控制 | 基于访问控制策略允许/拒绝数据包 | 防火墙白名单策略，规则精确到源地址、目的地址、端口与协议；策略变更走审批流程 |
| 入侵防范 | 在关键网络节点检测防御外部攻击 | 接入层限流与异常流量告警；登录接口、支付接口高频异常访问自动封禁；结合甲方边界安全设备联动 |
| 恶意代码防范 | 在关键节点对恶意代码检测清除 | 上传文件白名单校验+内容检测；服务器防病毒软件常驻查杀 |
| 安全审计 | 对重要用户行为与安全事件审计 | 边界访问日志、登录日志、操作日志全量留存不少于6个月，每周抽查审计 |

### 4.5.4 安全计算环境

安全计算环境是等保二级控制点最密集的层面，我方逐控制点落实如下：

| 控制点 | 二级控制要求 | 本项目落实措施 |
|---|---|---|
| 身份鉴别 | 身份标识唯一、鉴别信息复杂度、登录失败处理 | 账号实名唯一；口令复杂度技术强制并定期更换；登录失败次数限制与锁定；管理端会话超时自动登出 |
| 访问控制 | 账户权限分配、默认账户处理、最小权限 | RBAC角色权限模型，权限最小化；系统默认账户重命名或禁用、默认口令强制修改；离岗当日回收 |
| 安全审计 | 覆盖每个用户的安全审计、日志保护 | 登录/操作/接口日志覆盖全部用户与关键行为，记录事件时间、用户、类型、结果；日志防篡改、保存期不少于6个月 |
| 入侵防范 | 最小化安装、关闭多余端口、漏洞修补 | 操作系统与中间件最小化安装；端口最小开放；季度漏洞扫描+补丁评估更新流程（见4.1.2） |
| 恶意代码防范 | 安装防恶意代码软件并及时更新 | 服务器防病毒软件病毒库自动更新；上传目录禁止执行权限 |
| 数据完整性 | 采用校验技术保证重要数据传输/存储完整性 | 接口报文签名校验；支付/账单等资金数据落库前后勾稽校验；关键状态变更留痕 |
| 数据保密性 | 重要数据采用密码技术存储保护 | 身份证号等敏感字段加密存储、口令加盐哈希、密钥独立管理定期轮换 |
| 数据备份恢复 | 本地备份与恢复功能 | 每日全量+binlog增量备份、异机存放，每季度恢复演练（见4.4.4） |
| 剩余信息保护 | 鉴别信息与敏感数据存储空间释放前清除 | 会话注销即失效；临时文件用后即删；存储介质报废前安全擦除 |
| 个人信息保护 | 仅采集必要个人信息、访问与使用受控 | 按"最小必要"采集（详见4.6节个人信息保护专项设计） |

| 控制点 | 二级控制要求 | 本项目落实措施 |
|---|---|---|
| 系统管理 | 系统管理员身份鉴别、操作审计 | 运维操作统一经堡垒通道进行，命令级审计留痕；特权操作双人在场 |
| 审计管理 | 审计记录的存储、管理与查询 | 日志集中归集存储，审计员定期查询分析，审计报告月度输出 |

### 4.5.6 安全管理体系

等保二级对安全管理制度、管理机构、人员、建设管理、运维管理五个管理域的要求，我方对应落实如下：

## 4.6 个人信息与密码应用专项设计

### 4.6.1 个人信息保护专项

本系统涉及公民身份信息、社保婚姻学历等政务核验信息、支付信息，属于个人信息密集型系统。我方依据《个人信息保护法》《数据安全法》要求进行专项设计：

- **最小必要采集**：仅采集业务办理所必需的个人信息字段，资格核验数据仅取核验结论所需项，不留存政务侧原始全量数据；
- **告知同意**：用户首次使用时展示隐私政策并取得同意；资格核验前由用户签署承诺书授权数据调用（对应功能明细承诺书环节）；
- **全生命周期管控**：采集（加密传输）→存储（敏感字段加密）→使用（权限最小化+脱敏展示）→共享（仅限合同签章/支付等业务必需且经签名加密）→销毁（到期清理与安全擦除）逐环节受控；
- **用户权利响应**：支持用户查询本人信息；收到甲方转办的更正、删除类诉求后按流程限期处理；
- **员工侧约束**：全员保密承诺书覆盖个人信息条款，生产数据访问审批留痕，违规访问纳入安全责任追究。

### 4.6.2 密码应用设计

参照 GB/T 39786《信息安全技术 信息系统密码应用基本要求》对本系统密码应用进行设计：

| 应用环节 | 密码技术措施 |
|---|---|
| 传输保护 | 全站TLS 1.2+加密传输；与外部平台接口报文签名（防篡改）+关键字段加密（防泄露） |
| 存储保护 | 身份证号等敏感字段对称加密存储；用户口令加盐单向哈希，不可逆存储 |
| 身份鉴别 | JWT令牌签名防伪造；第三方回调验签；管理端登录图形验证码+失败锁定 |
| 完整性保护 | 电子合同经电子签章平台加盖可靠电子签名与时间戳，确保合同不可抵赖、不可篡改 |
| 密钥管理 | 密钥与代码分离存放、专人管理、权限受控；接口密钥按周期或人员变动轮换；密钥变更留痕 |

## 4.7 安全测试与验证

为验证上述安全措施有效落地，我方在测试阶段设置安全专项测试，典型安全测试用例如下：

| 用例编号 | 测试项 | 测试要点 | 预期结果 |
|---|---|---|---|
| TC-SEC-01 | SQL注入 | 对查询、登录、搜索类接口注入常见payload | 全部拦截，无异常回显，无数据泄露 |

| TC-SEC-03 | 横向越权 | 用户A携带自身令牌访问用户B的合同/账单/发票数据 | 返回无权限，越权行为记入日志 |
| TC-SEC-04 | 纵向越权 | 普通账号调用管理端接口 | 鉴权拦截，返回未授权 |

## 4.9 安全事件分级与报告时限

安全事件按影响程度分四级管理，报告与处置时限刚性执行：

| 事件等级 | 判定标准 | 报告时限 | 处置要求 |
|---|---|---|---|
| 特别重大 | 大规模个人信息泄露、系统被控、资金损失 | 立即口头报告甲方，1小时内书面报告 | 立即启动应急预案，隔离止损优先，公司级资源支援，配合监管报告义务 |
| 重大 | 高危漏洞被利用、局部数据泄露风险、页面篡改 | 2小时内报告甲方 | 24小时内完成处置与加固，输出事件报告 |
| 较大 | 高危漏洞发现（未被利用）、异常攻击流量 | 当日报告 | 24小时内完成高危漏洞处置；攻击源封禁与策略加固 |
| 一般 | 中低危漏洞、少量异常登录尝试 | 纳入周报 | 中危30天内修复，低危纳入迭代；持续监测 |

每起较大及以上安全事件执行"处置—根因—整改—复盘"闭环：处置完成后5个工作日内提交事件复盘报告（时间线、根因、损失评估、整改项与完成时限），整改项跟踪至闭环并在月度安全报告中呈现。

上述指标纳入月度安全报告向甲方呈报，接受甲方监督考核。通过"技术防控措施 + 八项管理制度 + 等保逐控制点落实 + 常态化安全运营"四位一体的安全解决方案，实现对系统漏洞、病毒、黑客攻击、管理制度缺陷四类风险的闭环管控。

## 5.2 运维制度

建立驻场运维制度体系，六项制度执行条款如下：

### 5.2.1 值班制度

1. 工作日驻场值守：驻场运维人员按甲方考勤要求现场办公，负责当日监控值守、工单响应与例行维护；
2. 非工作时间7×24小时远程响应：设置值班电话，告警自动推送值班人员；紧急故障远程处置，必要时1小时内赶赴现场；
3. 值班表每月编制并报甲方备案，调班须经项目经理批准并同步甲方；
4. 值班期间发生的事件、处置过程记入值班日志，次日晨会通报。

### 5.2.2 巡检制度

1. 日巡检：每工作日上午完成一轮标准巡检（详见5.7），填写《日巡检记录表》；
2. 周深度巡检：每周对性能趋势、慢查询、磁盘增长、证书有效期做深度检查，输出周报送；
3. 巡检发现异常按故障管理流程登记处置，重大隐患当日报甲方；
4. 巡检记录保存期与项目运维期一致，接受甲方抽查。

### 5.2.3 故障管理制度

1. 故障分级：按5.4节四级标准（紧急/严重/一般/轻微）定级，定级有争议时按高一级处理；
2. 响应与处置：紧急10分钟内响应、一般2小时内响应；处置优先恢复业务，再查根因；
3. 台账管理：全部故障录入《故障处理记录台账》（位置、问题、产生时间、解决时间、解决办法），邮件报送甲方备案；
4. 复盘改进：紧急与严重故障48小时内输出复盘报告，改进项闭环跟踪；
5. 升级机制：处置超时或影响扩大时，逐级升级至项目经理、公司二线专家团队。

### 5.2.4 备份制度

1. 每日自动备份（策略见5.11），备份结果纳入日巡检必查项；
2. 备份失败当日补备并排查原因；连续失败按严重故障处理；
3. 每季度恢复演练1次，演练报告报甲方；
4. 备份文件访问权限受控，加密存放，禁止擅自外拷。

### 5.2.5 报送制度

1. 周报送：每周输出运维工作报送（本周工作、故障与处置、下周计划）；
2. 月度运维报告：每月末前2个工作日邮件报送甲方备案，内容包括运维工作总结、故障统计分析、指标达成情况、容量与风险提示、运维建议；
3. 即时报送：紧急故障、安全事件在响应的同时立即电话+书面报甲方；
4. 报送材料统一归档，作为考核与审计依据。

### 5.2.6 交接班制度

1. 值班交接采用书面交接：未决事项、在途工单、注意事项逐项列明，接班人签字确认；
2. 人员轮换（休假、调整）时执行工作交接清单，项目经理复核；
3. 交接期间发生的事件责任界定以交接记录为准，避免"三不管"空档。

## 5.8 故障应急处置

制定分场景应急预案并定期演练（每半年不少于1次）：

| 场景 | 应急措施 |
|---|---|
| 应用服务宕机 | 进程自动拉起；无效则备节点接管，10分钟内恢复访问 |
| 数据库故障 | 主从切换预案；数据损坏时按备份恢复（RPO≤4小时，RTO≤2小时） |
| 支付渠道异常 | 启用支付降级提示，交易对账兜底，与渠道方联动排查 |
| 外部接口中断 | 资格核验自动降级人工审核；接口恢复后数据补偿 |
| 安全事件 | 立即隔离受影响节点、留存证据、上报甲方，按应急响应制度处置 |
| 高峰拥塞 | 集中配租等高峰前扩容预案、限流保护核心交易链路 |

典型场景的处置步骤卡如下，值班人员按卡执行、逐步打钩，避免紧急状态下的处置遗漏：

### 5.8.1 场景一：应用服务宕机处置卡

1. 【0-2分钟】确认告警真实性（健康检查、页面访问验证），排除误报；
2. 【2-5分钟】检查进程守护是否已自动拉起；已拉起则观察稳定性并进入根因排查；
3. 【5-10分钟】未自动恢复的，切换流量至备用节点，恢复对外服务；
4. 【恢复后】提取宕机时段日志（OOM、异常堆栈、资源曲线）定位根因；
5. 【当日】向甲方通报，48小时内输出复盘报告。

### 5.8.2 场景二：数据库故障处置卡

1. 【0-5分钟】确认故障类型：连接不可用/主从异常/数据损坏；
2. 【5-15分钟】连接类故障：重启实例或清理异常会话；主库不可用：执行主从切换预案，应用切换数据源；
3. 【数据损坏】立即停止写入，评估损坏范围，按"最近全量备份+binlog回放"恢复至故障前状态（RPO≤4小时、RTO≤2小时）；
4. 【恢复后】执行数据一致性核对脚本（账单、合同、房源状态勾稽），输出核对结果；
5. 【当日】向甲方通报，复盘并加固（如慢SQL治理、容量扩容）。

### 5.8.3 场景三：支付渠道异常处置卡

1. 【0-10分钟】监控确认支付回调成功率异常，区分我方故障与渠道方故障（渠道探测+我方日志）；
2. 【10-30分钟】我方故障立即修复回滚；渠道方故障启用前端降级提示（"支付渠道维护中"），同时联系渠道方技术；
3. 【处置中】对"用户已扣款、账单未核销"的在途交易挂起处理，禁止重复支付；
4. 【恢复后】执行专项对账：拉取渠道对账数据与我方支付单逐笔核对，差异交易按对账处理流程补单/退款；
5. 【当日】资金相关异常无论大小一律书面报甲方。

### 5.8.4 场景四：政务核验接口中断处置卡

1. 【0-10分钟】接口探测确认中断范围（单接口/全部），联系数据源侧确认；
2. 【10-30分钟】启用降级策略：资格核验切换"缓存结果 + 人工审核"模式，用户端提示"核验结果以人工复核为准"，业务不中断；
3. 【中断期间】记录降级期间产生的待复核清单；
4. 【恢复后】对降级期间数据批量重新核验，差异项转人工处置；
5. 【复盘】评估中断时长与影响面，必要时与数据源方完善联络与容错机制。

应急处置全程记录，事后48小时内输出故障复盘报告（原因、影响、处置过程、改进措施）。

### 5.11.2 恢复演练方案

### 6.2.3 关键路径与并行策略分析

60日历天工期的关键路径为：**需求冻结（第7天）→ 核心业务开发（选房-签约-支付链路）→ 外部接口联调（政务核验/支付/签章）→ 全链路联调（第52天）→ 数据迁移与切换（第57天）→ 初验（第60天）**。针对关键路径的专项管理措施：

| 关键路径环节 | 风险特征 | 并行/提前策略 |
|---|---|---|
| 外部接口开通 | 周期不受我方控制 | 第1周全部申请并行发起；未开通期间以挡板服务先行开发 |
| 政务核验联调 | 网络环境与数据授权依赖甲方协调 | 代理网关模式成熟复用；沙箱联调安排在第4-5周留足缓冲 |
| 支付/签章联调 | 涉及资金与法律效力，验证项多 | 我方成熟对接组件复用，联调重点收敛为参数适配与回归验证 |
| 数据迁移 | 数据质量不确定性 | 第2周即启动数据摸底与清洗规则制定，与开发并行推进；两轮演练前置 |
| 培训与验收资料 | 易被挤压后置 | 教材随迭代三并行编制；验收资料随里程碑同步沉淀 |

非关键路径任务（优惠券、消息、数据看板、报表等）在迭代计划中弹性调度，为关键路径让渡资源，保证整体工期刚性达成。

## 6.3 定制化开发期限保证

1. **需求快速冻结**：进场7天内完成需求基线签认，避免需求阶段拖期侵占开发窗口；
2. **成熟资产复用**：我方同类住房租赁平台成熟功能资产（约90%功能直接对应）+代码生成器，可将标准功能开发提速50%以上，是60天工期最有力的可行性保障；
3. **三轮迭代滚动交付**：每14天一个迭代，功能增量可视化验证，进度偏差在迭代粒度内即被发现与纠正；
4. **关键路径管理**：项目经理每日跟踪关键路径任务（外部对接、数据迁移），偏差超2天即启动纠偏（加班赶工、任务重排、增派人力）；
5. **人力弹性储备**：公司保持后备开发人力，进度告警时3个工作日内增援到岗，费用由我方承担。

## 6.4 部署实施期限保证

1. **环境先行**：开发/测试环境第1周就绪；生产环境部署方案第6周前与甲方评审确认，避免部署窗口临时协调；
2. **部署自动化**：标准化部署脚本+自动化流水线，单次部署耗时可控、过程可重复、失败可回滚；
3. **数据迁移预演**：不少于2轮试迁移演练，输出记录数/金额/抽样三级比对报告，正式切换选择业务低峰期执行，并制定回退预案；
4. **切换双保险**：新旧系统切换后保留旧系统只读查询，出现重大问题可快速回退，业务连续性有保障。

## 6.5 技术对接期限保证

1. **对接前置启动**：8类外部接口的接入申请、账号开通、沙箱环境申请在进场第1周并行发起，不等业务开发完成；
2. **对接经验复用**：我方已完成同类政务核验、支付渠道、电子签章、地图、微信平台的生产级对接，接口协议、联调要点、常见问题均有成熟预案，可大幅压缩联调周期；
3. **对接计划表管理**：每项对接明确甲方/第三方联系人、联调窗口、完成标准（沙箱联调→生产验证→回归测试），周例会逐项跟踪；
4. **风险缓冲设计**：对接受阻时启用降级方案先行保障主流程（如资格核验降级人工审核），不阻塞整体进度，待接口恢复后补齐联调。

## 6.6 测试培训期限保证

1. **测试左移**：测试工程师自迭代一即介入编写用例、执行迭代内测试，避免测试后置压缩周期；
2. **测试环境常备**：每日构建自动部署测试环境，回归测试自动化辅助，缩短回归周期；
3. **培训计划前置**：培训教材（操作手册、视频）随迭代三同步编制；采用"集中授课+现场辅导+常态答疑"组合，管理端按角色分批培训并组织上机考核，保证培训实效；
4. **验收测试预演**：正式验收前按验收标准逐项自查预演，问题先行整改，保证验收一次通过。

## 6.7 上线验收期限保证

1. **验收标准前置对齐**：进场后即与甲方确认初验、终验的标准与资料清单，验收资料随里程碑同步沉淀，不临时补造；
2. **试运行全程值守**：试运行期驻场团队现场值守，紧急问题10分钟响应，每日试运行日报，缺陷快速闭环；
3. **源代码交付质量**：交付源代码保证可独立编译生成与生产环境一致的可执行文件，代码结构清晰、注释完整、含编译部署脚本与说明文档，全力配合甲方源代码功能性验证与质量审查；
4. **验收资料完备**：需求、设计、测试、部署、操作手册、培训记录、迁移报告等全套文档按 GB/T 8567 规范编制，随验收一次性移交。
