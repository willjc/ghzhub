# 第一章 项目需求分析

## 1.1 项目建设背景

### 1.1.1 政策背景

近年来，国家高度重视住房保障体系建设，"租购并举"成为住房制度改革的核心方向。《国务院办公厅关于加快发展保障性租赁住房的意见》（国办发〔2021〕22号）明确提出加快完善以公租房、保障性租赁住房和共有产权住房为主体的住房保障体系；河南省、郑州市相继出台保障性租赁住房筹集建设与运营管理办法，要求以数字化手段提升保障性住房分配、运营、监管的效率与公平性。

郑州航空港经济综合实验区作为国家级航空经济先行区，产业人口快速集聚，人才公寓、保障性租赁住房、市场化租赁住房的供给规模持续扩大。传统依靠线下窗口受理、纸质档案管理、人工对账的房屋管理模式，已难以支撑多项目、多业态、大体量的租赁业务运营需求。

### 1.1.2 业务背景

郑州数据集团有限公司承担着区域房屋租赁业务的数字化运营职责。当前房屋租赁管理业务面临以下现实问题：

1. **业务流程线上化程度不足**：选房、签约、入住、退租、续租、缴费等核心业务环节仍存在线下办理、人工流转的情况，租户往返跑腿多、办理周期长；
2. **多业态管理口径不统一**：人才公寓、保租房、市场租赁三类业务在资格条件、配租方式、租金标准、审批流程上各不相同，缺乏统一的系统化承载；
3. **数据孤岛问题突出**：房源、合同、账单、租户数据分散管理，与郑好办用户体系、政务资格核验数据、支付渠道、电子签章等外部系统未打通，资格审核依赖人工线下核查；
4. **运营决策缺乏数据支撑**：出租率、收缴率、逾期率等关键经营指标无法实时统计，管理层缺少直观的数据看板；
5. **存量数据亟需迁移整合**：现有系统中的房屋、合同、账单、用户等港区业务数据需要平滑迁移至新系统，保证业务连续性。

### 1.1.3 项目定位

本项目通过采购研发团队驻场开发服务，构建包含**房源管理、合同管理、优惠券管理、消息管理、个人中心、运营中心、支付管理、数据看板**等业务的房屋管理系统，覆盖**移动端、小程序端、微信公众号端、后台管理端**四端，实现房屋租赁业务"申请—选房—签约—入住—居住服务—退租—结算"全生命周期线上化闭环，打造"数据多跑路、群众少跑腿"的智慧化房屋管理服务平台。

## 1.3 项目建设重难点解析

结合我方在同类保障性住房租赁管理平台建设中的实践经验，我们对本项目的重难点解析如下：

### 1.3.1 重点一：三类业态统一承载与差异化流程设计

人才公寓、保租房、市场租赁三类业务的主体流程同构（选房→签约→入住→退租→续租→缴费→开票），但在**资格校验规则**（人才公寓需人才认定，保租房需社保/婚姻/学历/住房多维核验，市场租赁仅查欠费）、**配租方式**（常规分配/集中分配/企业集中配租）、**审批链路**上存在显著差异。

**应对策略**：采用"统一业务模型 + 业务类型策略分流"的设计模式，合同、账单、房源使用统一数据模型并以业务类型字段区分，资格校验、续租校验等差异化环节采用策略模式按业务类型分流处理，既保证代码复用降低维护成本，又支持各业态规则独立演进。

### 1.3.2 重点二：多渠道政务数据对接与自动资格核验

保租房资格自动校验需要对接社保、婚姻、学历、住房、保租房共5类政务数据接口，接口分属不同层级（郑州市级/港区级），存在网络环境隔离、接口协议差异、响应时效不稳定等问题。

**应对策略**：我方在同类项目中已完整实现政务数据接口对接，采用"**政务接口代理网关**"模式：由部署于可访问政务网络环境的代理服务统一封装各政务接口，业务系统仅与代理网关交互；核验结果按业务规则设置合理缓存周期，减少重复调用；接口异常时自动降级为"人工审核"通道并给用户明确提示，保证业务不中断。该模式已在生产环境稳定运行，可低成本复用至本项目。

### 1.3.3 重点三：支付资金安全与账单准确性

押金、租金在线支付涉及资金安全，需处理支付回调丢失、重复支付、超时未支付、部分退款等复杂场景；账单生成需精确处理租期拆分、优惠券抵扣、逾期计算等规则，"押金未缴不可选租期账单缴费"等业务约束必须严格保证。

**应对策略**：基于我方成熟的支付对接经验，实施"**支付状态机 + 回调兜底 + 主动对账**"三重保障：订单状态机严格约束状态流转，防止重复支付；支付回调幂等处理，并以定时任务主动查询支付渠道补偿回调丢失；超时未支付订单自动取消释放房源；退款按账单明细拆分执行；每日与支付渠道对账，差异及时告警人工介入。

### 1.3.4 重点四：存量数据迁移的完整性与业务连续性

现有系统承载着在租合同、在途账单、历史缴费等生产数据，迁移过程必须保证数据不丢、不错、不重，且新旧系统切换期间业务不中断。

**应对策略**：我方具备同类系统老数据迁移的完整实战经验，采用"**分域清洗—映射转换—试迁移校验—增量补迁—并行核对**"五步迁移法：先对房屋、用户、合同、账单四大数据域分别制定清洗规则与字段映射表；在测试环境完成试迁移并输出比对报告（记录数、金额合计、关键字段抽样比对）；正式切换选择业务低峰期，切换后保留旧系统只读查询一段时间，用于并行核对与追溯。

### 1.3.5 重点五：多端一致性与低成本维护

移动端、小程序端、公众号端功能要求完全一致，若各端独立开发将造成约三倍的开发与维护成本，且极易出现多端行为不一致。

**应对策略**：采用 **uni-app 跨端统一开发框架**，一套代码编译产出 H5、微信小程序、公众号（H5内嵌）三端应用，业务逻辑、接口调用、页面交互完全一致；仅对人脸识别等平台差异能力做条件编译适配。该方案可显著压缩开发工期，并保证后续需求迭代"一处修改、三端生效"。

### 1.3.6 难点：驻场开发模式下的进度与质量双控

本项目开发期仅60日历天、总人月数不少于37人月，工期紧、任务重，且驻场开发需与甲方深度协同，需求确认、联调对接、验收节奏都依赖高效的协作机制。

**应对策略**：详见本方案第三章项目实施管理与第六章服务期限保证。核心措施包括：进场即冻结需求基线、按周迭代交付可视化成果、每日站会+每周例会双频同步、里程碑评审制、关键路径（政务接口/支付/电子签章对接）提前启动联调申请。

## 1.4 项目业务需求分析

### 1.4.1 业务角色分析

| 角色 | 说明 | 主要诉求 |
|---|---|---|
| 个人租户 | 人才公寓/保租房/市场租赁的申请人与承租人 | 线上完成资格申诉、选房、签约、缴费、开票、退租全流程，少跑腿、进度透明 |
| 企业客户 | 集中配租房源的承租单位 | 批量办理入住/退租、单位在线缴费 |
| 运营管理人员 | 甲方房屋租赁运营团队 | 房源台账清晰、审批高效、账单可催缴、报表可导出 |
| 财务人员 | 甲方财务部门 | 收款台账准确、退款流程可控、开票规范 |
| 系统管理员 | 平台管理与运维人员 | 权限精细可控、日志可追溯、配置灵活 |

### 1.4.2 核心业务流程需求

1. **资格申诉与核验**：系统自动调用政务接口核验资格（社保/婚姻/学历/住房/保租房），不符项支持用户手动刷新与在线申诉，管理端人工复核，形成"自动核验为主、人工审核兜底"的资格管理闭环；
2. **选房签约**：项目/房源浏览（含VR看房、地图导航）→ 签订承诺书 → 选定房源 →（人脸识别核验）→ 在线签署合同（电子签章）→ 押金缴纳（限时上传材料，超时自动退押解约）；
3. **入住管理**：入住申请 → 管理端签收审核 → 租户勾选房间物品核对状态 → 电子签字确认入住；
4. **居住服务**：投诉建议、保洁/搬家/报修订单在线申请，管理端分派服务公司，租户在线评价；
5. **退租结算**：退租申请 → 管理端签收 → 物品核对与退费信息确认 → 电子签字确认退租 → 退款申请、审批、退费；
6. **续租管理**：续租资格校验（资格+欠费）→ 续租合同在线签订 → 管理端审批 → 租金缴纳；
7. **账单缴费与开票**：账单自动生成 → 在线支付（支持优惠券抵扣）→ 逾期催缴 → 按账期申请开票 → 发票在线预览下载；
8. **运营管理**：配租批次管理、企业集中配租审批、黑名单管理、运营位配置、通知公告与政策文件发布。

## 2.6 系统接口设计

### 2.6.1 接口设计原则

统一采用 RESTful 风格 + JSON 报文；接口全部纳入 OpenAPI 3.0 在线文档；外部接口一律通过适配器层封装，做到"外部协议变化不侵入业务代码"；所有接口调用记录日志（请求方、时间、参数摘要、结果、耗时），可查可追溯。

### 2.6.2 郑好办用户体系对接

采用 OAuth2 授权模式对接郑好办统一用户体系：用户在移动端发起登录→跳转郑好办授权→回调携带授权码→后端换取访问令牌→获取用户身份信息→本地建立/关联用户档案→颁发系统 JWT 会话。令牌获取采用双重检查锁+Redis 缓存机制，避免并发重复请求；令牌到期自动刷新。对接时序如下图所示：

![图2-6 郑好办用户体系对接时序图](images/08-郑好办对接时序图.png)

### 2.6.3 政务数据资格核验对接

通过政务接口代理网关对接社保（郑州市）、婚姻（郑州市）、学历（郑州市）、住房（港区）、保租房（港区）5类核验接口以及房管局、不动产权中心公共数据接口：

- 代理网关部署于可访问政务网络的环境，统一鉴权、统一报文转换、统一日志留痕；
- 核验结果结构化落库并缓存，支持用户手动刷新重新核验；
- 接口不可用时自动降级人工审核通道，业务不中断；
- 敏感个人信息按最小必要原则调用，传输全程加密。

## 2.7 系统安全设计

系统安全设计贯穿身份认证（郑好办统一认证+JWT+会话管理）、访问控制（RBAC菜单/按钮/数据三级权限）、传输安全（全站HTTPS）、数据安全（敏感字段加密存储、脱敏展示）、应用安全（SQL注入/XSS/CSRF防护、接口签名与幂等）、审计安全（登录/操作/接口日志全留痕）六个层面，整体按照网络安全等级保护二级标准设计建设。详细安全解决方案见本方案第四章"系统安全管理"。

### 3.1.3 人员保障机制

- **AB角备份**：关键岗位（项目经理、架构师、核心后端）设置AB角，A角不可用时B角24小时内到岗接替；

## 3.2 开发规划

### 3.2.1 开发模式

采用"迭代式开发 + 里程碑管控"模式：将60日历天开发期划分为需求确认、迭代开发（3轮）、系统联调、试运行准备等阶段，每轮迭代交付可运行、可演示的功能增量，甲方全程可见、可试用、可纠偏，避免"最后一刻才见系统"的交付风险。

### 3.2.2 开发阶段规划

| 阶段 | 工作内容 | 交付物 |
|---|---|---|
| 需求确认（第1周） | 需求宣讲、原型确认、需求基线冻结、数据迁移调研 | 需求规格说明书、原型稿、迁移方案 |

注：第三方接口（政务核验、支付渠道、电子签章、人脸识别）的接入申请、参数开通等外部依赖事项在第1周即并行启动，不占用关键路径。

### 3.2.3 需求管理

需求基线冻结后实行变更受控（见3.4节）；建立需求跟踪矩阵，实现"招标功能清单211项 → 需求规格 → 开发任务 → 测试用例 → 验收项"全链路双向追溯，确保功能不漏项、验收有依据。

## 3.3 开发测试与协作管理

### 3.3.1 协作机制

- **每日站会**（15分钟）：同步昨日进展、当日计划、阻塞问题；
- **每周例会**：与甲方共同评审周进度、演示迭代成果、确认下周计划，输出周报；
- **里程碑评审**：每个迭代结束由甲方参与评审，签署阶段确认意见；
- **问题台账**：需求疑问、外部依赖、风险事项统一登记跟踪，明确责任人与解决时限。

### 3.3.2 测试管理

实行"开发自测 → 提测准入 → 集成测试 → 回归测试 → 验收测试"五级测试流程：

| 测试类型 | 内容 |
|---|---|
| 功能测试 | 依据需求跟踪矩阵逐项覆盖211项功能，用例评审后执行 |
| 接口测试 | 内部接口与8类外部接口的正向/异常/边界场景测试 |
| 业务流程测试 | 选房签约、入住退租、缴费开票等端到端全流程串测 |
| 兼容性测试 | 主流手机机型、微信版本、小程序/公众号环境、主流PC浏览器 |
| 性能测试 | 核心接口压测（集中配租选房高峰场景），验证响应时间与并发指标 |
| 安全测试 | 越权访问、SQL注入、XSS、敏感信息泄露等安全用例（详见第四章） |
| 数据迁移测试 | 试迁移记录数/金额合计/关键字段抽样三级比对 |

缺陷按严重/一般/轻微三级管理，严重缺陷24小时内修复，版本发布前严重与一般缺陷清零。

### 3.3.3 质量保证

代码走查与评审（合并前强制评审）、编码规范静态检查、单元测试覆盖核心业务逻辑、每日构建冒烟测试；质量数据（缺陷密度、修复时长、用例通过率）纳入周报向甲方透明呈现。

## 3.4 配置与变更管理

### 3.4.1 配置管理

- **版本控制**：全部源代码、数据库脚本、配置文件、文档纳入 Git 统一管理；采用分支模型（主干保护+功能分支+发布分支），合并须经代码评审；
- **持续集成/持续部署**：搭建自动化流水线，代码提交自动触发编译、静态检查、自动化部署到测试环境，发布过程标准化、可重复、可回滚（该流水线为我方同类项目生产环境验证过的成熟实践）；
- **配置项标识**：版本号规范化管理，每次发布输出版本说明（变更内容、影响范围、回滚方案）；
- **环境配置分离**：开发/测试/生产环境参数外部化，杜绝硬编码，敏感配置（密钥、口令）加密管理。

### 3.4.2 变更管理

需求/设计/计划变更执行"申请—影响评估—审批—实施—验证—关闭"闭环流程：变更申请书面提出，项目经理组织评估对工期、成本、质量的影响，报甲方审批后实施，变更结果回归验证并更新需求跟踪矩阵与基线文档。紧急变更（生产缺陷修复）可先行处置、48小时内补办手续。

## 3.5 技术规范管控

- **编码规范**：Java 开发遵循业界通用编码规约，前端遵循 Vue/uni-app 官方风格指南，静态扫描工具纳入流水线强制检查；
- **数据库规范**：表结构设计评审制，命名规范、索引规范、变更脚本版本化管理，禁止生产库手工变更；
- **接口规范**：RESTful 设计规范 + OpenAPI 3.0 文档强制同步更新，接口变更须评审并通知联调方；
- **安全规范**：敏感数据处理规范、日志脱敏规范、密钥管理规范（详见第四章）；
- **文档规范**：按 GB/T 8567 编制需求、设计、测试、部署、操作手册等全套文档，随里程碑同步交付。

## 3.6 部署对接及运行测试保障

- **环境保障**：进场第1周完成开发、测试环境搭建；生产环境部署方案（服务器规划、网络策略、域名证书、备份策略）提前与甲方评审确认；
- **对接保障**：为8类外部对接（郑好办、政务核验、支付、签章、人脸、地图、监控、微信平台）分别建立对接联系人清单与联调计划表，接口开通申请提前发起；每项对接完成"沙箱联调→生产验证→回归测试"三步确认；
- **数据迁移保障**：迁移演练不少于2轮，正式切换安排在业务低峰期，制定分步切换与回退预案，旧系统保留只读查询用于并行核对；
- **试运行保障**：试运行期间驻场团队全程值守，建立问题快速响应通道（紧急10分钟响应），每日输出试运行日报；
- **验收保障**：按招标验收标准与合同约定组织初验、终验，交付源代码（可独立编译、注释完整、含编译部署脚本与说明文档）及全套文档，配合甲方源代码功能性验证与质量审查。

## 3.7 低成本、标准化实现系统互联互通

我方以"标准优先、复用优先、配置优先"三原则实现系统互联互通的低成本落地：

1. **标准化接口体系**：全部对外/对内接口采用 RESTful + JSON 统一标准，OpenAPI 3.0 文档自动生成，第三方接入无需定制开发即可完成联调，降低双方对接成本；
2. **适配器模式隔离外部差异**：支付、签章、人脸、地图、监控等外部能力均以适配器封装，更换服务商仅需替换适配器实现，业务代码零改动，避免供应商锁定带来的重复建设成本；
3. **政务接口代理网关复用**：我方已建成并在生产环境稳定运行的政务数据代理网关（统一鉴权、报文转换、缓存、降级、日志），可直接复用于本项目的资格核验与公共数据对接，节省该部分从零开发成本；
4. **成熟平台底座复用**：统一权限、字典、日志、代码生成、任务调度等平台能力为我方成熟资产，直接复用，将人力集中投入业务功能开发；
5. **模板化数据交换**：批量导入导出、数据迁移采用标准 Excel 模板 + 校验回执机制，与甲方既有办公习惯无缝衔接，无需额外采购数据交换工具。

## 4.1 系统漏洞风险防控

### 4.1.1 开发阶段漏洞预防

- **安全编码规范**：强制执行输入校验、输出编码、参数化查询（MyBatis-Plus 预编译杜绝SQL拼接）、文件上传白名单校验（类型/大小/重命名存储）、反序列化限制等安全编码要求；
- **框架级防护**：Spring Security 统一认证鉴权，接口默认拒绝匿名访问；全局 XSS 过滤器对请求参数净化；CSRF 防护与同源校验；
- **依赖组件治理**：建立第三方组件清单，版本纳入配置管理；上线前执行依赖漏洞扫描，高危组件（如存在已公开CVE）强制升级或替换；
- **代码安全审计**：静态代码扫描纳入CI流水线，安全类缺陷阻断合并；核心模块（认证、支付、资格核验）人工安全评审。

### 4.1.2 运行阶段漏洞管理

- **漏洞扫描**：系统上线前及运行期定期（每季度）开展主机漏洞扫描与Web应用漏洞扫描，输出扫描报告；
- **渗透测试**：上线前配合甲方或第三方机构开展渗透测试，问题限期整改复测；
- **补丁管理**：操作系统、中间件、数据库补丁评估—测试环境验证—生产窗口期更新的三步流程，重大安全补丁48小时内完成评估；
- **漏洞响应**：收到漏洞通报（甲方、监管、CNVD等渠道）后，高危漏洞24小时内完成处置或临时缓解措施。

## 4.2 病毒风险防控

- **服务器侧**：生产服务器安装防病毒软件并保持病毒库自动更新，定期全盘查杀；最小化安装原则关闭无关服务与端口，禁用未授权外设与移动介质；
- **应用侧**：文件上传统一经过类型白名单校验、内容检测与重命名隔离存储，上传目录禁止执行权限，从源头阻断WebShell与带毒文件；
- **终端侧**：驻场开发终端统一安装防病毒软件，接入甲方网络前完成安全检查，遵守甲方终端管理规定；
- **传播阻断**：网络分区隔离（见4.3），关键服务器间仅开放必要端口，病毒即使侵入也难以横向扩散。

## 4.3 黑客攻击风险防控

### 4.3.1 网络边界防护

- **防火墙策略**：边界防火墙白名单策略，仅开放业务必需端口（443等）；管理端口（SSH、数据库）禁止公网暴露，仅限运维专用通道访问；
- **网络分区**：按"接入区—应用区—数据区"划分安全域（VLAN隔离），数据库仅接受应用服务器网段访问；
- **DDoS与流量防护**：接入层限流（Nginx 连接数/请求速率限制），异常流量告警，必要时联动上游清洗服务；
- **传输加密**：全站 HTTPS（TLS 1.2+），证书规范管理，杜绝明文传输。

### 4.3.2 应用层攻击防护

- **认证安全**：登录失败次数限制与账户锁定、验证码机制、JWT 令牌签名校验与有效期控制、会话超时自动登出、同账号异地登录检测；
- **接口安全**：接口鉴权全覆盖（横向越权校验到数据行级）、支付/签约等敏感接口幂等与防重放（时间戳+随机数+签名）、第三方回调验签；
- **暴力破解防护**：管理端登录接口速率限制，弱口令策略强制（长度、复杂度、定期更换）；
- **入侵检测与审计**：登录日志、操作日志、接口调用日志全量留存（保存期不少于6个月），异常行为（高频失败登录、异常时段操作、批量导出）告警。

### 4.3.3 数据安全防护

- **加密存储**：身份证号等敏感字段加密存储，口令加盐哈希，密钥独立管理并定期轮换；
- **脱敏展示**：身份证、手机号在前端展示与日志输出中统一脱敏（该规范为我方生产系统既有实践）；
- **权限最小化**：数据库账号按应用/运维/备份分权，禁用超级账号跑业务；管理端数据权限按部门/角色收敛；
- **防泄漏**：批量导出功能权限单独控制并留痕；测试环境使用脱敏数据，禁止生产数据出域。

## 4.4 管理制度缺陷风险防控

建立与技术措施配套的安全管理制度体系：

| 制度 | 核心内容 |
|---|---|
| 安全责任制度 | 项目经理为安全第一责任人，岗位安全职责书面化，全员签订保密承诺书 |
| 账号权限管理制度 | 账号实名唯一、权限最小化、离岗即回收、特权账号双人管理、权限季度复核 |
| 上线发布管理制度 | 发布申请—审批—窗口期执行—验证—回滚预案，禁止未经审批的生产变更 |
| 数据管理制度 | 数据分级分类、备份与恢复演练、生产数据访问审批、导出留痕 |
| 日志审计制度 | 日志集中留存、定期审计、异常事件溯源分析 |
| 安全教育制度 | 人员进场安全培训、季度安全意识教育、钓鱼与社工防范演练 |
| 第三方管理制度 | 外部接口对接安全评估、供应商访问受控、接口密钥定期轮换 |
| 应急响应制度 | 安全事件分级、响应流程、上报机制、事后复盘（与第五章应急预案衔接） |

## 4.5 等保二级安全控制措施

对照 GB/T 22239-2019 二级要求，逐层落实安全控制措施：

| 等保层面 | 主要控制措施 |
|---|---|
| 安全物理环境 | 依托甲方机房/云平台的物理访问控制、防火防水防雷、电力保障能力 |
