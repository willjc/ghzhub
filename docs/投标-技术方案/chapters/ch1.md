# 第一章 项目需求分析

## 1.1 项目建设背景

### 1.1.1 政策背景

近年来，国家高度重视住房保障体系建设，"租购并举"成为住房制度改革的核心方向。《国务院办公厅关于加快发展保障性租赁住房的意见》（国办发〔2021〕22号）明确提出加快完善以公租房、保障性租赁住房和共有产权住房为主体的住房保障体系；河南省、郑州市相继出台保障性租赁住房筹集建设与运营管理办法，要求以数字化手段提升保障性住房分配、运营、监管的效率与公平性。

郑州航空港经济综合实验区作为国家级航空经济先行区，产业人口快速集聚，人才公寓、保障性租赁住房、市场化租赁住房的供给规模持续扩大。传统依靠线下窗口受理、纸质档案管理、人工对账的房屋管理模式，已难以支撑多项目、多业态、大体量的租赁业务运营需求。

本项目建设所依据的主要政策文件如下表所示：

| 层级 | 政策文件 | 与本项目的关联要点 |
|---|---|---|
| 国家 | 《国务院办公厅关于加快发展保障性租赁住房的意见》（国办发〔2021〕22号） | 明确保障性租赁住房基础制度与支持政策，要求提升租赁住房管理服务水平 |
| 国家 | 《"十四五"公共服务规划》 | 要求扩大保障性租赁住房供给，完善住房保障服务体系 |
| 国家 | 《关于加强新市民、青年人等群体住房保障工作的意见》 | 聚焦新市民、青年人住房困难问题，要求简化准入审核流程 |
| 国家 | 《"数字中国"建设整体布局规划》 | 要求推进公共服务数字化、普惠化，政务服务"一网通办" |
| 行业 | 《住房和城乡建设部关于加强轻资产住房租赁企业监管的意见》 | 对租赁资金、租金监管提出规范化要求 |
| 河南省 | 《河南省加快发展保障性租赁住房实施方案》 | 明确全省保租房筹集目标与运营管理要求 |
| 郑州市 | 《郑州市保障性租赁住房运营管理办法》 | 规定保租房申请条件、审核程序、租金标准、退出机制 |
| 郑州市 | 《郑州市人才公寓建设管理办法》 | 规定人才公寓的申请资格、配租程序、优惠政策 |
| 港区 | 郑州航空港经济综合实验区保租房、人才公寓管理现行办法 | 本项目资格校验、配租流程、租金政策的直接业务依据 |
| 数字政务 | 郑州市"郑好办"一体化政务服务平台建设要求 | 要求各类民生服务接入郑好办统一用户体系，实现"一次认证、全网通办" |

从政策导向可以看出：**住房保障业务的"数字化、平台化、协同化"是明确的建设方向**——资格审核要与政务数据打通实现"免证明"，业务办理要向移动端迁移实现"掌上办"，运营管理要以数据为支撑实现"精细化"。本项目正是上述政策要求在郑州航空港经济综合实验区住房租赁领域的具体落地。

### 1.1.2 业务背景

郑州数据集团有限公司承担着区域房屋租赁业务的数字化运营职责。当前房屋租赁管理业务面临以下现实问题：

1. **业务流程线上化程度不足**：选房、签约、入住、退租、续租、缴费等核心业务环节仍存在线下办理、人工流转的情况，租户往返跑腿多、办理周期长；
2. **多业态管理口径不统一**：人才公寓、保租房、市场租赁三类业务在资格条件、配租方式、租金标准、审批流程上各不相同，缺乏统一的系统化承载；
3. **数据孤岛问题突出**：房源、合同、账单、租户数据分散管理，与郑好办用户体系、政务资格核验数据、支付渠道、电子签章等外部系统未打通，资格审核依赖人工线下核查；
4. **运营决策缺乏数据支撑**：出租率、收缴率、逾期率等关键经营指标无法实时统计，管理层缺少直观的数据看板；
5. **存量数据亟需迁移整合**：现有系统中的房屋、合同、账单、用户等港区业务数据需要平滑迁移至新系统，保证业务连续性。

上述问题对各方主体的影响分析如下：

| 影响对象 | 现状问题带来的影响 | 数字化改造后的预期改善 |
|---|---|---|
| 租户（个人） | 资格审核周期长，需线下提交证明材料；选房、签约、缴费需多次跑现场；办理进度不透明 | 政务数据自动核验"免证明"，全流程掌上办理，进度实时可查 |
| 企业客户 | 批量入住/退租依靠线下名单流转，办理效率低、易出错 | 名单模板在线上传、批量办理，审批流程线上留痕 |
| 运营管理人员 | 房源台账手工维护，配租组织依靠电话与表格，审批流转慢 | 房源状态实时联动，配租批次在线管理，审批一键流转 |
| 财务人员 | 对账依赖人工核对流水，退款流程长，开票手工登记 | 支付渠道自动对账，退款在线审批，开票申请与交付线上化 |
| 管理决策层 | 经营数据靠事后统计报表，时效性差、口径不一 | 数据看板实时呈现出租率、收缴率、逾期率等核心指标 |
| 监管与审计 | 纸质档案调阅困难，操作过程难以追溯 | 全流程电子留痕，操作日志可查可追溯 |

### 1.1.3 项目定位

本项目通过采购研发团队驻场开发服务，构建包含**房源管理、合同管理、优惠券管理、消息管理、个人中心、运营中心、支付管理、数据看板**等业务的房屋管理系统，覆盖**移动端、小程序端、微信公众号端、后台管理端**四端，实现房屋租赁业务"申请—选房—签约—入住—居住服务—退租—结算"全生命周期线上化闭环，打造"数据多跑路、群众少跑腿"的智慧化房屋管理服务平台。

围绕上述定位，我方将本项目的建设目标细化为一个总目标与五个分项目标：

**总目标**：在60日历天开发期内，建成覆盖四端、承载三类租赁业态、贯通八大业务域的房屋管理系统，完成存量数据迁移与八项外部系统对接，通过验收后提供6年免费驻场运维服务，支撑港区房屋租赁业务长期稳定运行。

| 分项目标 | 目标描述 | 衡量标准 |
|---|---|---|
| 业务全流程线上化 | 选房、签约、入住、退租、续租、缴费、开票等核心业务全部线上办理 | 211项功能明细全部实现并通过验收 |
| 资格核验自动化 | 保租房、人才公寓资格通过政务数据接口自动核验 | 社保/婚姻/学历/住房/保租房五维自动校验上线，人工审核兜底 |
| 多端体验一致化 | 移动端、小程序端、公众号端功能与体验完全一致 | 三端功能项覆盖率100%，同一业务多端办理结果一致 |
| 数据资产完整化 | 存量业务数据完整迁移，经营数据实时可视 | 迁移数据比对一致率100%，数据看板核心指标实时更新 |
| 运行保障长效化 | 建立驻场运维体系，保障系统长期稳定 | 年可用率≥99.5%，紧急故障10分钟响应，免费运维6年 |

## 1.3 项目建设重难点解析

结合我方在同类保障性住房租赁管理平台建设中的实践经验，我们对本项目的重难点解析如下：

### 1.3.1 重点一：三类业态统一承载与差异化流程设计

人才公寓、保租房、市场租赁三类业务的主体流程同构（选房→签约→入住→退租→续租→缴费→开票），但在**资格校验规则**（人才公寓需人才认定，保租房需社保/婚姻/学历/住房多维核验，市场租赁仅查欠费）、**配租方式**（常规分配/集中分配/企业集中配租）、**审批链路**上存在显著差异。

**应对策略**：采用"统一业务模型 + 业务类型策略分流"的设计模式，合同、账单、房源使用统一数据模型并以业务类型字段区分，资格校验、续租校验等差异化环节采用策略模式按业务类型分流处理，既保证代码复用降低维护成本，又支持各业态规则独立演进。

### 1.3.2 重点二：多渠道政务数据对接与自动资格核验

保租房资格自动校验需要对接社保、婚姻、学历、住房、保租房共5类政务数据接口，接口分属不同层级（郑州市级/港区级），存在网络环境隔离、接口协议差异、响应时效不稳定等问题。

**应对策略**：我方在同类项目中已完整实现政务数据接口对接，采用"**政务接口代理网关**"模式：由部署于可访问政务网络环境的代理服务统一封装各政务接口，业务系统仅与代理网关交互；核验结果按业务规则设置合理缓存周期，减少重复调用；接口异常时自动降级为"人工审核"通道并给用户明确提示，保证业务不中断。该模式已在生产环境稳定运行，可低成本复用至本项目。

### 1.3.3 重点三：支付资金安全与账单准确性

押金、租金在线支付涉及资金安全，需处理支付回调丢失、重复支付、超时未支付、部分退款等复杂场景；账单生成需精确处理租期拆分、优惠券抵扣、逾期计算等规则，"押金未缴不可选租期账单缴费"等业务约束必须严格保证。

**应对策略**：基于我方成熟的支付对接经验，实施"**支付状态机 + 回调兜底 + 主动对账**"三重保障：订单状态机严格约束状态流转，防止重复支付；支付回调幂等处理，并以定时任务主动查询支付渠道补偿回调丢失；超时未支付订单自动取消释放房源；退款按账单明细拆分执行；每日与支付渠道对账，差异及时告警人工介入。

### 1.3.4 重点四：存量数据迁移的完整性与业务连续性

现有系统承载着在租合同、在途账单、历史缴费等生产数据，迁移过程必须保证数据不丢、不错、不重，且新旧系统切换期间业务不中断。

**应对策略**：我方具备同类系统老数据迁移的完整实战经验，采用"**分域清洗—映射转换—试迁移校验—增量补迁—并行核对**"五步迁移法：先对房屋、用户、合同、账单四大数据域分别制定清洗规则与字段映射表；在测试环境完成试迁移并输出比对报告（记录数、金额合计、关键字段抽样比对）；正式切换选择业务低峰期，切换后保留旧系统只读查询一段时间，用于并行核对与追溯。

### 1.3.5 重点五：多端一致性与低成本维护

移动端、小程序端、公众号端功能要求完全一致，若各端独立开发将造成约三倍的开发与维护成本，且极易出现多端行为不一致。

**应对策略**：采用 **uni-app 跨端统一开发框架**，一套代码编译产出 H5、微信小程序、公众号（H5内嵌）三端应用，业务逻辑、接口调用、页面交互完全一致；仅对人脸识别等平台差异能力做条件编译适配。该方案可显著压缩开发工期，并保证后续需求迭代"一处修改、三端生效"。

### 1.3.6 难点：驻场开发模式下的进度与质量双控

本项目开发期仅60日历天、总人月数不少于37人月，工期紧、任务重，且驻场开发需与甲方深度协同，需求确认、联调对接、验收节奏都依赖高效的协作机制。

**应对策略**：详见本方案第三章项目实施管理与第六章服务期限保证。核心措施包括：进场即冻结需求基线、按周迭代交付可视化成果、每日站会+每周例会双频同步、里程碑评审制、关键路径（政务接口/支付/电子签章对接）提前启动联调申请。

### 1.4.2 核心业务流程需求

#### 1.4.2.1 资格申诉与核验流程

系统自动调用政务接口核验资格，不符项支持用户手动刷新与在线申诉，管理端人工复核，形成"自动核验为主、人工审核兜底"的资格管理闭环。

| 环节 | 参与角色 | 流程要求 |
|---|---|---|
| 自动核验 | 系统 | 用户发起申请后，自动调用社保（郑州市）、婚姻（郑州市）、学历（郑州市）、住房（港区）、保租房（港区）核验接口，逐项返回核验结果 |
| 不符项展示 | 租户 | 核验不通过项以列表形式明确展示，注明不符原因 |
| 手动刷新 | 租户 | 用户补正信息后（如社保补缴到账）可手动触发重新核验 |
| 在线申诉 | 租户 | 对核验结果有异议的，在线提交申诉说明与佐证材料 |
| 人工复核 | 运营管理人员 | 管理端受理申诉，人工审核后录入复核结论，结论回写资格状态 |
| 记录留痕 | 系统 | 每次核验、申诉、复核均留存记录，支持导出审计 |

#### 1.4.2.2 选房签约流程

项目/房源浏览（含VR看房、地图导航）→ 签订承诺书 → 选定房源 →（人脸识别核验）→ 在线签署合同（电子签章）→ 押金缴纳（限时上传材料，超时自动退押解约）。流程关键需求点：

- 房源列表须按楼栋/单元/房间层级展示，支持户型、朝向、楼层等条件筛选；
- 房源详情提供照片、公示信息、周边配套、VR看房、地图导航、管家电话，信息充分辅助决策；
- 选房前须在线签订承诺书；小程序/公众号端签约前进行人脸识别，核验签约人与选房人一致；
- 合同采用电子签章在线签署，签署完成支持在线下载；
- 押金缴纳设置时限，同时限时上传要求材料，超时系统自动退还押金并取消合同、释放房源。

#### 1.4.2.3 入住办理流程

入住申请 → 管理端签收审核 → 租户勾选房间物品核对状态 → 电子签字确认入住。要求物品核对清单由系统按房源设施配置自动生成，租户逐项勾选核对，签字确认后形成入住确认单存档；企业客户支持上传入住人员名单模板批量办理。

#### 1.4.2.4 居住服务流程

投诉建议、保洁/搬家/报修订单在线申请，管理端分派服务公司，租户在线评价。要求服务订单全程状态可查（已申请/已分派/服务中/已完成/已评价），服务公司作为独立管理对象支持增删改查与服务范围配置。

#### 1.4.2.5 退租结算流程

退租申请 → 管理端签收 → 物品核对与退费信息确认 → 电子签字确认退租 → 退款申请、审批、退费。要求退费金额由系统按租期自动计算并支持人工调整留痕；退款须经审批流程，审批通过后原路退回；管理端另需支持强制退租处理能力。

#### 1.4.2.6 续租管理流程

续租资格校验（人才公寓/保租房校验资格+欠费，市场租赁仅校验欠费）→ 续租合同在线签订 → 管理端审批 → 租金缴纳提示。要求续租校验规则按业态差异化配置，校验不通过时明确提示不通过原因。

#### 1.4.2.7 账单缴费与开票流程

账单自动生成 → 在线支付（支持优惠券抵扣）→ 逾期催缴 → 按账期申请开票 → 发票在线预览下载。关键约束：**押金账单未缴清前不允许选择租期账单缴费**；支付对接港区支付接口，支持第三方在线支付；优惠券抵扣金额自动计算；管理端支持按账单维度催缴并记录催缴历史。

#### 1.4.2.8 运营管理流程

配租批次管理（新增/编辑/作废/审批/详情）、企业客户集中配租、黑名单管理、金刚位/轮播图/腰封位/广告位运营配置、通知公告与政策文件发布。要求集中配租支持房源与人员的批量绑定与审批流转，运营位配置实时生效。

**（3）安全需求细化**：整体满足GB/T 22239-2019等保二级要求；身份证号、手机号等个人敏感信息加密存储、界面脱敏展示、导出受控；登录鉴权采用统一认证+会话超时控制；权限按角色最小化授权并支持数据权限隔离；登录日志与操作日志全量留存且不可篡改，保存期限满足审计要求。

**（4）易用性需求细化**：移动端交互面向普通租户设计，关键业务（选房、签约、缴费）操作步骤清晰、状态提示明确；表单校验即时反馈，错误提示语义友好；管理端列表支持多条件筛选、排序、导出，高频操作路径不超过3次点击；对老年用户等群体保证字体可读性与操作容错。

### 1.4.4 需求理解的三个关键判断

基于对招标需求的整体分析，我方形成以下三个关键判断，并以此指导方案设计：

1. **本项目是"业务平台"而非"信息展示系统"**：211项功能中约80%涉及业务流转、状态变更与资金往来，系统设计必须以业务状态机、审批流、资金安全为核心，而非简单的信息增删改查；
2. **对接质量决定项目成败**：郑好办、政务核验、支付、签章、人脸识别、地图、监控、公共数据8类对接贯穿核心流程，任何一个对接不畅都会阻断主业务链路，因此对接工作必须提前启动、并行推进、预设降级方案；
3. **迁移与并行期是风险最集中的阶段**：存量在租合同与在途账单迁移后必须立即可用，切换期间的每一笔缴费都不能出错，必须以演练充分、可回退的迁移方案保障平稳过渡。

**（7）系统管理**：用户/账号/角色/权限（菜单权限+数据权限）/字典/消息管理（渠道+队列）/安全日志（登录日志、操作日志可查可追溯），为全系统提供统一的权限与配置底座。

### 1.5.3 实施与对接需求

数据迁移（房屋/合同/账单/用户数据）、系统使用培训、公共数据接口对接（房管局/不动产权中心）、地图对接、资格核验接口对接、监控对接、支付渠道对接、电子签章对接、公众号端与小程序端构建、人脸识别调用，共11项。

### 1.5.4 功能需求理解小结

我方已逐项研读全部211项功能明细，并与我方已建成运行的同类住房租赁管理平台功能体系进行了逐项比对：**约90%的功能项与我方已有成熟实现直接对应**（选房签约、入住退租、账单支付、开票、配租批次、企业集中配租、服务订单、数据看板等），其余功能项（优惠券核销体系、自定义报表、监控对接等）我方已有清晰的技术实现路径。这使我方能够以"成熟方案定制化适配"取代"从零开发"，在60日历天开发期内高质量完成交付。

## 1.6 系统非功能性需求分析

除功能性需求外，本项目作为面向公众的政务服务类系统，对性能、可用性、兼容性、易用性、可扩展性与安全合规均有较高要求。我方对非功能性需求的分析与设计指标承诺如下：

### 1.6.1 性能需求

| 指标项 | 指标要求 | 设计保障措施 |
|---|---|---|
| 页面响应时间 | 普通页面≤2秒，复杂查询页面≤3秒 | 接口瘦身、懒加载、CDN静态资源分发 |
| 接口响应时间 | 一般业务接口≤500ms（P95），查询类接口≤1秒（P95） | 索引优化、热点数据Redis缓存、读写分离 |
| 并发能力 | 支持≥1000用户在线、≥200并发事务，选房高峰场景专项压测 | 应用无状态多实例部署、连接池调优、异步削峰 |
| 批量处理 | 万级房源/租户数据导入导出≤5分钟，异步任务不阻塞在线业务 | 异步任务队列+分批处理+进度反馈 |
| 报表统计 | 看板指标秒级返回，明细报表万级数据导出≤3分钟 | 统计走只读从库与预聚合，导出异步生成 |
| 高峰承载 | 配租批次开放选房瞬时高峰不宕机、不超卖 | 房源锁定原子化（Redis+数据库双重约束）、排队削峰 |

### 1.6.2 可用性与可靠性需求

| 指标项 | 指标要求 | 设计保障措施 |
|---|---|---|
| 系统年可用率 | ≥99.5% | 关键组件冗余部署、健康检查、自动故障转移 |
| 故障响应 | 紧急故障10分钟内响应，一般故障2小时内响应 | 驻场值守+监控告警三级推送+应急处置卡 |
| 数据可靠性 | RPO≤4小时、RTO≤2小时 | 每日全量+日间增量备份、异机存放、每季度恢复演练 |
| 事务一致性 | 资金相关操作强一致，支付零差错 | 支付状态机+回调幂等+每日对账三重保障 |
| 容错能力 | 外部接口故障不导致主流程中断 | 适配器隔离、超时熔断、降级人工通道 |

### 1.6.3 兼容性需求

| 维度 | 兼容要求 |
|---|---|
| 移动端浏览器 | 微信内置浏览器、主流手机浏览器（基于WebKit/Blink内核）全兼容 |
| 微信生态 | 微信小程序基础库近两年主流版本；公众号网页授权规范 |
| 管理端浏览器 | Chrome、Edge、360（极速模式）、火狐等主流现代浏览器 |
| 屏幕适配 | 移动端主流分辨率自适应；管理端1366×768及以上分辨率适配 |
| 操作系统 | 服务端兼容主流Linux发行版；客户端不限操作系统 |

### 1.6.4 易用性需求

1. **面向公众的低门槛设计**：办事流程步骤化引导、表单项通俗化命名、必要处提供示例与说明，中老年用户也可顺畅完成申请、缴费操作；
2. **状态透明**：申请审核、合同签署、退租退款等在途业务全程进度可视，减少用户电话咨询；
3. **防错设计**：关键操作二次确认、表单实时校验即时提示、超时操作自动保存草稿；
4. **管理端效率设计**：高频审批操作支持批量处理，列表页记忆查询条件，导出模板与页面所见一致。

### 1.6.5 可扩展性与可维护性需求

1. **业务可扩展**：业务类型策略化设计，新增业态（如新增配租政策类型）仅需扩展策略实现而不改动主干代码；
2. **能力可替换**：支付、签章、地图等外部能力适配器化，更换服务商不影响业务层；
3. **配置驱动**：运营位、合同模板、消息模板、审批规则等以配置管理，运营调整零发版；
4. **可观测性**：日志、指标、链路三位一体，问题定位从"小时级"缩短到"分钟级"；
5. **文档与注释**：交付代码注释完整、文档齐套，保障甲方后续自主维护与二次开发。

### 1.6.6 安全合规需求

系统需满足网络安全等级保护二级要求，遵循《网络安全法》《数据安全法》《个人信息保护法》相关规定：身份鉴别、访问控制、安全审计、数据加密、个人信息最小化采集与脱敏展示、日志留存不少于6个月。详细安全设计见本方案第四章。

| 术语 | 定义 |
|---|---|
| 四端应用 | 移动端（H5）、微信小程序端、微信公众号端、后台管理端的合称 |

| 挡板服务 | 外部接口未开通期间用于模拟其请求响应行为的测试替身服务 |

| RPO/RTO | 灾难恢复指标：最大可容忍数据丢失时长/最大可容忍业务中断时长 |
| 等保二级 | 网络安全等级保护第二级，本系统的安全建设与测评基准 |
| 初验/终验 | 初步验收（开发交付后）与最终验收（按合同约定条件达成后）
