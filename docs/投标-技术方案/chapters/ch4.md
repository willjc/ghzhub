# 第四章 系统安全管理

我方按照网络安全等级保护二级（GB/T 22239-2019）要求，构建"技术防控 + 管理制度"双轮驱动的安全解决方案，对系统漏洞、病毒、黑客攻击、管理制度缺陷四类风险实施针对性防控。安全防护整体架构如下图所示：

## 4.1 系统漏洞风险防控

### 4.1.1 开发阶段漏洞预防

- **安全编码规范**：强制执行输入校验、输出编码、参数化查询（MyBatis-Plus 预编译杜绝SQL拼接）、文件上传白名单校验（类型/大小/重命名存储）、反序列化限制等安全编码要求；
- **框架级防护**：Spring Security 统一认证鉴权，接口默认拒绝匿名访问；全局 XSS 过滤器对请求参数净化；CSRF 防护与同源校验；
- **依赖组件治理**：建立第三方组件清单，版本纳入配置管理；上线前执行依赖漏洞扫描，高危组件（如存在已公开CVE）强制升级或替换；
- **代码安全审计**：静态代码扫描纳入CI流水线，安全类缺陷阻断合并；核心模块（认证、支付、资格核验）人工安全评审。

### 4.1.2 运行阶段漏洞管理

- **漏洞扫描**：系统上线前及运行期定期（每季度）开展主机漏洞扫描与Web应用漏洞扫描，输出扫描报告；
- **渗透测试**：上线前配合甲方或第三方机构开展渗透测试，问题限期整改复测；
- **补丁管理**：操作系统、中间件、数据库补丁评估—测试环境验证—生产窗口期更新的三步流程，重大安全补丁48小时内完成评估；
- **漏洞响应**：收到漏洞通报（甲方、监管、CNVD等渠道）后，高危漏洞24小时内完成处置或临时缓解措施。

### 4.1.3 安全基线配置规范

我方为生产环境各组件制定安全基线，部署时逐项核对、运行期定期复查：

**操作系统基线（Linux）**：

| 基线项 | 配置要求 |
|---|---|
| 账号策略 | 禁用直接root远程登录；运维账号实名；口令复杂度与有效期策略生效 |
| 服务最小化 | 关闭无关系统服务；卸载无关软件包；仅开放业务必需端口 |
| SSH加固 | 修改默认端口、密钥登录优先、失败锁定、登录超时 |
| 审计配置 | 开启系统审计（auditd），记录特权命令与关键文件变更 |
| 内核参数 | 关闭ICMP重定向、开启SYN Cookie等防护参数 |

**中间件基线（Nginx）**：

| 基线项 | 配置要求 |
|---|---|
| 版本信息隐藏 | 关闭版本号回显（server_tokens off） |
| TLS配置 | 仅启用TLS 1.2+，禁用弱加密套件 |
| 限流防护 | 连接数限制、请求速率限制、请求体大小限制 |
| 安全响应头 | X-Frame-Options、X-Content-Type-Options、CSP等安全头统一下发 |
| 目录防护 | 禁止目录浏览；上传目录禁止执行脚本 |

**数据库基线（MySQL）**：

| 基线项 | 配置要求 |
|---|---|
| 网络访问 | 仅监听内网地址，仅授权应用服务器网段访问 |
| 账号分权 | 应用/运维/备份/只读账号分离，禁用匿名账号，应用账号无DDL权限 |
| 口令策略 | 强口令、定期更换、禁止硬编码明文（配置加密存储） |
| 日志审计 | 开启慢查询日志、错误日志；关键库表变更留痕 |
| 备份加密 | 备份文件加密存储、异机存放、权限受控 |

**缓存基线（Redis）**：

| 基线项 | 配置要求 |
|---|---|
| 访问控制 | 仅内网监听、启用密码认证、禁用危险命令（FLUSHALL/CONFIG等重命名） |
| 数据安全 | 不存储明文敏感数据；键设置合理过期时间 |

**应用基线（Spring Boot）**：

| 基线项 | 配置要求 |
|---|---|
| 配置安全 | 生产配置与代码分离，数据库口令、接口密钥加密存放 |
| 接口安全 | actuator等管理端点关闭或鉴权保护；Swagger生产环境关闭 |
| 错误处理 | 统一异常处理，生产环境不回显堆栈信息 |
| 日志安全 | 敏感字段输出统一脱敏；日志级别生产环境为INFO及以上 |

## 4.2 病毒风险防控

- **服务器侧**：生产服务器安装防病毒软件并保持病毒库自动更新，定期全盘查杀；最小化安装原则关闭无关服务与端口，禁用未授权外设与移动介质；
- **应用侧**：文件上传统一经过类型白名单校验、内容检测与重命名隔离存储，上传目录禁止执行权限，从源头阻断WebShell与带毒文件；
- **终端侧**：驻场开发终端统一安装防病毒软件，接入甲方网络前完成安全检查，遵守甲方终端管理规定；
- **传播阻断**：网络分区隔离（见4.3），关键服务器间仅开放必要端口，病毒即使侵入也难以横向扩散。

**防病毒部署矩阵**：

| 部署对象 | 防护措施 | 病毒库更新 | 查杀策略 |
|---|---|---|---|
| 应用服务器 | 服务器防病毒软件+最小化安装+端口白名单 | 每日自动更新 | 每周全盘查杀，日志留存 |
| 数据库服务器 | 防病毒软件（排除数据文件目录防误杀）+访问白名单 | 每日自动更新 | 每周全盘查杀（业务低峰执行） |
| 文件存储目录 | 上传文件类型白名单+内容检测+重命名隔离+禁执行权限 | — | 上传即检、定期复扫 |
| 驻场办公终端 | 统一防病毒软件+补丁管理+移动介质管控 | 每日自动更新 | 每周查杀+接入前检查 |

**病毒安全事件处置流程**：发现（告警/巡检）→ 隔离（受染主机断网或访问隔离）→ 查杀（专杀工具处置，无法清除则重装）→ 溯源（感染途径分析，堵住入口）→ 恢复（业务验证后恢复接入）→ 报告（2小时内向甲方报告事件与处置结果，形成事件报告归档）。全程处置动作留痕，重大病毒事件按应急预案（见第五章）升级处置。

**日常管理要求**：每周巡检核查各节点病毒库版本与查杀日志；禁止在生产服务器安装与运行无关软件；外来文件（含甲方提供的数据文件）先查毒后使用；病毒防控执行情况纳入月度安全运营报告。

## 4.3 黑客攻击风险防控

系统构建"网络边界—应用—数据"三层纵深防御体系，如下图所示：

![图4-2 纵深防御体系图](images/30-纵深防御体系图.png)

### 4.3.1 网络边界防护

- **防火墙策略**：边界防火墙白名单策略，仅开放业务必需端口（443等）；管理端口（SSH、数据库）禁止公网暴露，仅限运维专用通道访问；
- **网络分区**：按"接入区—应用区—数据区"划分安全域（VLAN隔离），数据库仅接受应用服务器网段访问；
- **DDoS与流量防护**：接入层限流（Nginx 连接数/请求速率限制），异常流量告警，必要时联动上游清洗服务；
- **传输加密**：全站 HTTPS（TLS 1.2+），证书规范管理，杜绝明文传输。

### 4.3.2 应用层攻击防护

- **认证安全**：登录失败次数限制与账户锁定、验证码机制、JWT 令牌签名校验与有效期控制、会话超时自动登出、同账号异地登录检测；
- **接口安全**：接口鉴权全覆盖（横向越权校验到数据行级）、支付/签约等敏感接口幂等与防重放（时间戳+随机数+签名）、第三方回调验签；
- **暴力破解防护**：管理端登录接口速率限制，弱口令策略强制（长度、复杂度、定期更换）；
- **入侵检测与审计**：登录日志、操作日志、接口调用日志全量留存（保存期不少于6个月），异常行为（高频失败登录、异常时段操作、批量导出）告警。

### 4.3.3 数据安全防护

- **加密存储**：身份证号等敏感字段加密存储，口令加盐哈希，密钥独立管理并定期轮换；
- **脱敏展示**：身份证、手机号在前端展示与日志输出中统一脱敏（该规范为我方生产系统既有实践）；
- **权限最小化**：数据库账号按应用/运维/备份分权，禁用超级账号跑业务；管理端数据权限按部门/角色收敛；
- **防泄漏**：批量导出功能权限单独控制并留痕；测试环境使用脱敏数据，禁止生产数据出域。

### 4.3.4 渗透测试与攻防演练

- **上线前渗透测试**：上线前委托内部安全团队按OWASP TOP 10开展渗透测试，覆盖认证绕过、越权访问、注入攻击、文件上传、逻辑漏洞（支付金额篡改、优惠券滥用）等场景，输出渗透测试报告，高危漏洞清零后方可上线；
- **运维期年度渗透测试**：每年度开展1次渗透测试复测，覆盖新增功能与历史修复项回归；
- **攻防演练配合**：积极配合甲方及监管部门组织的网络安全攻防演练（如护网行动），演练期间提高监测等级、专人值守，演练发现问题限期整改闭环；
- **安全应急演练**：每年组织不少于1次安全事件应急演练（模拟WebShell植入、数据库拖库、勒索攻击等场景），检验监测发现、隔离处置、恢复报告全流程有效性，演练报告报送甲方。

## 4.4 管理制度缺陷风险防控

建立与技术措施配套的安全管理制度体系：

| 制度 | 核心内容 |
|---|---|
| 安全责任制度 | 项目经理为安全第一责任人，岗位安全职责书面化，全员签订保密承诺书 |
| 账号权限管理制度 | 账号实名唯一、权限最小化、离岗即回收、特权账号双人管理、权限季度复核 |
| 上线发布管理制度 | 发布申请—审批—窗口期执行—验证—回滚预案，禁止未经审批的生产变更 |
| 数据管理制度 | 数据分级分类、备份与恢复演练、生产数据访问审批、导出留痕 |
| 日志审计制度 | 日志集中留存、定期审计、异常事件溯源分析 |
| 安全教育制度 | 人员进场安全培训、季度安全意识教育、钓鱼与社工防范演练 |
| 第三方管理制度 | 外部接口对接安全评估、供应商访问受控、接口密钥定期轮换 |
| 应急响应制度 | 安全事件分级、响应流程、上报机制、事后复盘（与第五章应急预案衔接） |

八项制度的执行条款如下：

### 4.4.1 安全责任制度（执行条款）

1. 项目经理为项目安全第一责任人，对项目全周期安全工作负总责；架构师兼任安全技术负责人，负责安全设计与技术措施落地；运维工程师为日常安全运行责任人；
2. 各岗位安全职责以《岗位安全职责书》书面明确，人员进场时签署确认；
3. 全体项目人员进场前签订个人保密承诺书，承诺不泄露甲方业务数据、系统资料与个人信息，保密义务在离场后持续有效；
4. 每季度开展安全责任落实情况检查，检查结果与人员考核挂钩；
5. 发生安全责任事故，按"事故原因未查清不放过、责任人未处理不放过、整改措施未落实不放过、相关人员未受教育不放过"原则处理。

### 4.4.2 账号权限管理制度（执行条款）

1. 系统账号（应用、数据库、服务器、中间件）实行实名制，一人一号，禁止共用；
2. 权限按最小必要原则授予：申请—审批—授权—记录四步流程，审批人须为该系统权限归口负责人；
3. 特权账号（数据库管理员、服务器root）实行双人管理：口令分段保管，使用须双人在场并登记《特权操作记录单》；
4. 人员离岗（离职、调岗、项目撤出）当日回收全部账号权限，运维工程师执行、项目经理复核；
5. 每季度开展权限复核：输出账号清单与权限矩阵，逐一确认"账号在用、权限匹配岗位"，冗余权限限期清理；
6. 口令策略：长度与复杂度强制要求、定期更换、禁止默认口令与弱口令，系统层面技术强制。

### 4.4.3 上线发布管理制度（执行条款）

1. 生产变更一律走发布流程：《发布申请单》（变更内容、影响范围、验证方案、回滚方案）→项目经理审批→甲方确认（重大变更）→窗口期执行；
2. 发布窗口原则上安排在业务低峰期；涉及停机的发布提前通知甲方并公告用户；
3. 发布执行采用标准化流水线（自动化部署），发布过程双人操作（一人执行、一人复核）；
4. 发布后执行验证清单（核心流程冒烟测试），验证通过方可宣布发布完成；验证不通过立即执行回滚方案；
5. 紧急缺陷修复可走紧急发布通道：口头报备即可执行，48小时内补齐发布单据；
6. 每次发布输出《版本说明》归档，全年发布记录可审计。

### 4.4.4 数据管理制度（执行条款）

1. 数据分级：按敏感程度将数据分为公开、内部、敏感、重要四级，个人身份信息、资格核验信息、支付信息列为敏感级及以上；
2. 敏感数据访问实行审批制：生产数据查询/修数/导出须提交工单，说明用途、范围、时限，审批通过后在监督下执行并全程留痕；
3. 备份策略：数据库每日全量+binlog增量备份，备份文件异机存储；每季度至少1次恢复演练并输出演练报告；
4. 数据导出：批量导出功能权限单独控制，导出记录（操作人、时间、数据范围、行数）留痕可审计；
5. 测试数据管理：测试环境一律使用脱敏数据，禁止生产数据未脱敏出域；
6. 数据销毁：存储介质报废前执行数据安全擦除；临时数据文件用后即删。

### 4.4.5 日志审计制度（执行条款）

1. 日志范围：登录日志、操作日志、接口调用日志、系统运行日志、安全设备日志全量采集；
2. 日志集中管理：各节点日志统一归集存储，保存期不少于6个月；日志文件权限受控、禁止篡改删除；
3. 定期审计：运维工程师每周开展日志抽查审计（异常登录、越权尝试、批量导出、异常时段操作），每月输出审计报告；
4. 异常处置：审计发现可疑行为立即溯源分析，确认为安全事件的按应急响应制度处置并上报甲方；
5. 日志脱敏：日志输出中的证件号、手机号等敏感字段统一脱敏，防止日志成为泄露源。

### 4.4.6 安全教育制度（执行条款）

1. 进场教育：全员进场时完成安全培训（甲方安全规定、保密要求、安全编码规范、终端安全要求），考核通过方可上岗；
2. 季度教育：每季度组织安全意识教育（近期安全事件案例、钓鱼邮件识别、口令安全、办公区安全）；
3. 专项演练：每年组织钓鱼与社会工程学防范演练，演练结果通报并针对性补课；
4. 新规宣贯：甲方安全管理规定更新时，5个工作日内完成全员宣贯签认。

### 4.4.7 第三方管理制度（执行条款）

1. 对接安全评估：新增外部接口对接前开展安全评估（认证方式、传输加密、数据范围、留痕能力），评估通过方可对接；
2. 密钥管理：与第三方交换的接口密钥、证书专人保管、加密存储，按约定周期或人员变动时轮换；
3. 访问受控：第三方人员确需访问项目环境的，须甲方批准、限定范围与时限、全程陪同与留痕；
4. 供应商变更：第三方服务变更（版本升级、协议调整）须提前评估影响并回归测试后生效。

### 4.4.8 应急响应制度（执行条款）

1. 事件分级：按影响范围与严重程度将安全事件分为重大、较大、一般三级；
2. 响应时限：紧急事件10分钟内响应，一般事件2小时内响应；
3. 处置流程：发现/接报→初步研判定级→先行止损（隔离、封禁、降级）→上报甲方→根因排查→恢复验证→事后复盘报告；
4. 上报机制：重大事件立即电话+书面双通道上报甲方安全归口部门，处置进展持续同步；
5. 复盘改进：每起事件输出复盘报告（时间线、根因、损失评估、整改项），整改项闭环跟踪（详细应急预案见第五章）。

### 4.4.9 制度执行监督与检查机制

制度的价值在于执行。我方建立"自查+互查+专项检查+外部审计"四层监督机制，确保上述八项管理制度不流于纸面：

| 检查层级 | 检查主体 | 频次 | 检查内容 | 结果处理 |
|---|---|---|---|---|
| 日常自查 | 各岗位人员 | 每日 | 本岗位制度执行情况随工作日志自查申报 | 异常事项当日上报直接负责人 |
| 交叉互查 | 项目组内互查 | 每月 | 账号权限、日志完整性、备份有效性、发布记录合规性 | 互查发现问题限期3个工作日整改 |
| 专项检查 | 项目经理+安全负责人 | 每季度 | 按制度逐条对照检查，输出《制度执行检查表》 | 检查结果纳入人员季度考核；重大偏差报公司质量部门 |
| 外部审计配合 | 甲方/第三方审计机构 | 按甲方安排 | 配合等保测评、审计检查，提供全部留痕材料 | 审计意见逐条整改并书面反馈 |

**制度执行检查表（模板摘要）**：检查表按八项制度设置检查项，每项标注"符合/基本符合/不符合"三档结论与证据索引（日志编号、审批单编号、记录表编号），检查人与被检查人双签确认。典型检查项包括：离岗人员账号是否在当日禁用、特权操作是否双人复核留痕、备份恢复演练是否按季度执行并有记录、发布是否均有审批单与回退预案、安全教育是否按计划开展并有签到记录等。

**持续改进闭环**：每季度专项检查后召开制度评审会，对检查中暴露的制度缺陷（条款缺失、职责不清、流程不顺）进行修订，修订版本报甲方备案后发布执行，形成"执行—检查—改进—再执行"的PDCA闭环。

## 4.6 个人信息与密码应用专项设计

### 4.6.1 个人信息保护专项

本系统涉及公民身份信息、社保婚姻学历等政务核验信息、支付信息，属于个人信息密集型系统。我方依据《个人信息保护法》《数据安全法》要求进行专项设计：

- **最小必要采集**：仅采集业务办理所必需的个人信息字段，资格核验数据仅取核验结论所需项，不留存政务侧原始全量数据；
- **告知同意**：用户首次使用时展示隐私政策并取得同意；资格核验前由用户签署承诺书授权数据调用（对应功能明细承诺书环节）；
- **全生命周期管控**：采集（加密传输）→存储（敏感字段加密）→使用（权限最小化+脱敏展示）→共享（仅限合同签章/支付等业务必需且经签名加密）→销毁（到期清理与安全擦除）逐环节受控；
- **用户权利响应**：支持用户查询本人信息；收到甲方转办的更正、删除类诉求后按流程限期处理；
- **员工侧约束**：全员保密承诺书覆盖个人信息条款，生产数据访问审批留痕，违规访问纳入安全责任追究。

### 4.6.2 密码应用设计

参照 GB/T 39786《信息安全技术 信息系统密码应用基本要求》对本系统密码应用进行设计：

| 应用环节 | 密码技术措施 |
|---|---|
| 传输保护 | 全站TLS 1.2+加密传输；与外部平台接口报文签名（防篡改）+关键字段加密（防泄露） |
| 存储保护 | 身份证号等敏感字段对称加密存储；用户口令加盐单向哈希，不可逆存储 |
| 身份鉴别 | JWT令牌签名防伪造；第三方回调验签；管理端登录图形验证码+失败锁定 |
| 完整性保护 | 电子合同经电子签章平台加盖可靠电子签名与时间戳，确保合同不可抵赖、不可篡改 |
| 密钥管理 | 密钥与代码分离存放、专人管理、权限受控；接口密钥按周期或人员变动轮换；密钥变更留痕 |

## 4.7 安全测试与验证

为验证上述安全措施有效落地，我方在测试阶段设置安全专项测试，典型安全测试用例如下：

| 用例编号 | 测试项 | 测试要点 | 预期结果 |
|---|---|---|---|
| TC-SEC-01 | SQL注入 | 对查询、登录、搜索类接口注入常见payload | 全部拦截，无异常回显，无数据泄露 |
| TC-SEC-02 | XSS攻击 | 表单与富文本字段提交脚本代码 | 输出统一编码/过滤，脚本不执行 |
| TC-SEC-03 | 横向越权 | 用户A携带自身令牌访问用户B的合同/账单/发票数据 | 返回无权限，越权行为记入日志 |
| TC-SEC-04 | 纵向越权 | 普通账号调用管理端接口 | 鉴权拦截，返回未授权 |
| TC-SEC-05 | 暴力破解 | 管理端登录连续错误口令尝试 | 触发失败锁定与告警 |
| TC-SEC-06 | 文件上传绕过 | 上传伪装扩展名的可执行文件 | 白名单+内容检测拦截，上传目录不可执行 |
| TC-SEC-07 | 支付防重放 | 重复提交同一支付回调报文 | 幂等处理，账单不重复核销 |
| TC-SEC-08 | 敏感信息泄露 | 检查接口响应、日志、错误页中的证件号/手机号 | 统一脱敏，错误页不暴露堆栈 |
| TC-SEC-09 | 会话安全 | 令牌过期、注销后旧令牌重放 | 旧令牌全部失效拒绝 |
| TC-SEC-10 | 弱口令检测 | 对全部系统账号执行弱口令扫描 | 无弱口令、无默认口令 |

安全测试问题纳入缺陷管理流程（见3.3.4），安全类缺陷一律按严重级别处理，未清零不允许上线；上线前配合甲方或第三方机构完成渗透测试并整改复测。

| 每季 | 漏洞扫描、权限全量复核、安全意识教育、安全责任落实检查、备份恢复演练 | 季度扫描报告、权限复核表、恢复演练报告 |

## 4.9 安全事件分级与报告时限

安全事件按影响程度分四级管理，报告与处置时限刚性执行：

| 事件等级 | 判定标准 | 报告时限 | 处置要求 |
|---|---|---|---|
| 特别重大 | 大规模个人信息泄露、系统被控、资金损失 | 立即口头报告甲方，1小时内书面报告 | 立即启动应急预案，隔离止损优先，公司级资源支援，配合监管报告义务 |
| 重大 | 高危漏洞被利用、局部数据泄露风险、页面篡改 | 2小时内报告甲方 | 24小时内完成处置与加固，输出事件报告 |
| 较大 | 高危漏洞发现（未被利用）、异常攻击流量 | 当日报告 | 24小时内完成高危漏洞处置；攻击源封禁与策略加固 |

每起较大及以上安全事件执行"处置—根因—整改—复盘"闭环：处置完成后5个工作日内提交事件复盘报告（时间线、根因、损失评估、整改项与完成时限），整改项跟踪至闭环并在月度安全报告中呈现。

上述指标纳入月度安全报告向甲方呈报，接受甲方监督考核。通过"技术防控措施 + 八项管理制度 + 等保逐控制点落实 + 常态化安全运营"四位一体的安全解决方案，实现对系统漏洞、病毒、黑客攻击、管理制度缺陷四类风险的闭环管控。
