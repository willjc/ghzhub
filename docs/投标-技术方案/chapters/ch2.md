## 2.2 系统组成

系统由"四端应用 + 八大业务域 + 三类支撑平台"组成：

**（1）四端应用**：移动端（H5）、微信小程序端、微信公众号端、后台管理端（PC Web）。三个用户端基于 uni-app 跨端框架统一开发，功能完全一致；后台管理端基于 Vue + Element UI 构建。

**（2）八大业务域**：房源管理、合同管理、优惠券管理、消息管理、个人中心、运营中心、支付管理、数据看板。

**（3）三类支撑平台**：
- **基础支撑平台**：统一权限（RBAC，菜单权限+数据权限）、字典管理、参数配置、代码生成、定时任务调度、操作日志与安全审计；
- **集成支撑平台**：郑好办认证适配器、政务数据代理网关、支付网关适配器、电子签章适配器、人脸识别适配器、地图服务适配器、监控视频适配器、消息推送渠道（站内信/模板消息/短信）；
- **数据支撑平台**：MySQL 主数据库、Redis 缓存、文件存储服务、数据备份与迁移工具集。

## 2.3 系统结构

系统采用前后端分离的分层架构设计，自上而下分为用户终端层、访问网关层、前端表现层、业务服务层、核心支撑层、数据持久层、第三方接口层，共七层。系统总体架构如下图所示：

![图2-2 系统总体架构图](images/01-系统总体架构图.png)

各层设计说明：

| 层次 | 组成 | 设计要点 |
|---|---|---|
| 用户终端层 | H5/小程序/公众号/PC浏览器 | 多终端接入，响应式适配 |
| 访问网关层 | Nginx 反向代理 | HTTPS 卸载、负载均衡、静态资源缓存、限流防护 |
| 前端表现层 | uni-app 三端 + Vue 管理端 | 组件化开发、路由权限控制、接口统一封装 |
| 业务服务层 | Spring Boot 业务应用 | 八大业务域 RESTful 服务，Controller-Service-Mapper 分层 |
| 核心支撑层 | Spring Security、MyBatis-Plus、Quartz、消息队列 | 认证授权、ORM、定时任务（账单生成/合同到期/超时取消）、异步解耦 |
| 数据持久层 | MySQL 主从 + Redis + 文件存储 | 读写分离、热点缓存、附件/VR文件存储 |
| 第三方接口层 | 郑好办/政务核验/支付/签章/人脸/地图/监控 | 适配器模式封装，可插拔替换 |

该架构具有以下特点：

1. **成熟稳定**：基于业界广泛验证的 Java 技术体系（Spring Boot 3 + Spring Security + MyBatis-Plus + MySQL + Redis），我方已有同类系统在生产环境长期稳定运行；
2. **模块化、高内聚低耦合**：业务域之间通过服务接口交互，第三方能力通过适配器隔离，便于扩展与替换；
3. **信创兼容**：技术栈全面兼容信创环境，可平滑适配国产数据库（达梦、人大金仓）、国产操作系统（麒麟）、国产中间件（东方通），满足后续国产化演进要求；
4. **弹性可扩展**：应用无状态设计，会话集中存储于 Redis，支持横向扩容应对集中配租等高峰场景。

## 2.5 核心业务功能设计

以下按八大业务域展开功能设计（功能项与招标功能清单211项逐一对应）。

### 2.5.0 功能设计方法说明

为保证功能设计与招标功能明细严格对应、便于评审核对，本节采用统一的设计描述框架：每个业务域先给出**设计概述与设计目标**，再按功能点给出**逐项功能设计表**，表格字段约定如下：

| 字段 | 说明 |
|---|---|
| 功能点 | 与招标"软件开发清单及功能明细"对应的功能名称 |
| 功能设计说明 | 功能的页面构成、操作流程、系统处理逻辑 |
| 关键业务规则 | 该功能必须满足的约束条件、校验规则、状态联动 |

所有功能点的数据操作均遵守统一的通用设计约定，不在逐项表中重复描述：

1. **权限约定**：管理端每个功能均受RBAC权限控制（菜单可见性、按钮操作权、数据范围权三级）；用户端功能均需登录后访问（政策浏览类除外）；
2. **留痕约定**：所有新增、修改、删除、审批、导出操作均记录操作日志（操作人、时间、对象、内容摘要）；
3. **列表约定**：管理端列表页均支持多条件组合查询、分页、排序；带导出功能的列表导出字段与查询结果一致；
4. **表单约定**：所有表单前后端双重校验，必填项、格式、长度、数值范围校验规则一致；
5. **状态约定**：涉及状态流转的业务对象（房源、合同、账单、订单、审批单）均采用状态机管理，非法状态跳转一律拒绝并留痕。

### 2.5.1 房源管理

**设计概述**：房源管理是全系统的资产数据底座，建立"项目→楼栋→单元→房源"四级资产台账，向上支撑选房、签约、入住业务，向下联动数据看板的出租率统计。设计目标：资产账实一致、房源状态与业务实时联动、配租方式灵活可配。

逐项功能设计如下：

| 功能点 | 功能设计说明 | 关键业务规则 |
|---|---|---|
| 项目管理 | 管理端维护小区/产业园/厂房三类项目档案：项目基础信息（名称、地址、经纬度、业态类型、管理办法）、项目图片、周边配套说明；支持增删改查、Excel导入导出 | 项目地址与地图坐标联动校验；项目下存在在租房源时不允许删除 |
| 房型管理 | 按项目维护房型（户型名称、居室、面积、朝向、装修标准、户型图、租金标准），房源关联房型自动继承属性 | 房型被房源引用时变更需二次确认；面积、租金为必填数值 |
| 房源管理 | 房源档案增删改查、批量导入导出；上下架控制；管家电话维护；精选房源标记；定向配租时间设置；VR文件上传与管理 | 上架必须信息完整（照片、租金、房型）；下架不影响在租合同；VR文件校验格式与大小 |
| 房源状态机 | 空置、已预订（选房锁定）、已出租、维修中、下架五状态流转；选房锁定设有效期，支付超时自动释放回空置 | 状态流转全部由业务动作驱动，禁止手工直接改状态（特殊场景走批量状态变更审批）；同一房源同一时刻仅允许一个有效锁定，防一房多租 |
| 常规分配 | 租户自主浏览房源→选房→签约的开放式配租通道 | 仅"空置+已上架+符合业态可见性规则"的房源可被选择 |
| 集中分配（配租批次） | 配租批次新增/编辑/作废/审批/详情：绑定房源清单与人员名单，批次内人员在配租时间窗内选房 | 批次房源在窗口期内仅对批次内人员可见；批次作废自动释放未选房源；批次操作走审批流 |
| 企业客户集中配租 | 面向企业客户的批量配租：企业信息+集中分配房源清单绑定，企业端在线缴费、批量入住 | 企业配租房源不进入个人选房池；企业欠费时限制新增配租 |
| 预约看房管理 | 用户端在线预约看房，管理端签收/确认预约并安排带看 | 同一用户对同一项目的有效预约不重复创建；预约状态变化触发消息通知 |
| VR看房 | 管理端按房源/房型上传VR全景文件，用户端房源详情内嵌VR漫游 | VR资源CDN分发按需加载，不阻塞详情页首屏 |
| 地图找房 | 房源地图点位聚合展示，按区域/小区/户型筛选，按人才公寓/保租房/市场化业态筛选，点击跳转房源详情，支持导航 | 地图点位数据与房源上下架状态实时同步 |

**页面与交互设计要点**：管理端房源列表采用"树形项目导航+列表"双栏布局，支持按楼栋/单元下钻；房源批量导入提供标准Excel模板与导入校验报告（成功/失败明细）；用户端房源列表卡片展示核心决策信息（租金、面积、朝向、楼层、标签），详情页信息分区呈现（照片轮播/公示信息/周边配套/VR入口/位置导航/管家电话一键拨打）。

### 2.5.2 合同管理

**设计概述**：合同管理承载租赁关系的法律载体，覆盖"模板配置→在线签署→履行管理→续租/变更→到期/解除"全生命周期，对接电子签章保证合同法律效力。设计目标：签署流程合规可信、合同状态自动管控、多类型合同统一台账。

逐项功能设计如下：

| 功能点 | 功能设计说明 | 关键业务规则 |
|---|---|---|
| 合同模板配置 | 管理端按项目/业态配置合同模板：付款周期（月付/季付/半年付/年付）、签约期限、押金金额等签约要素；模板版本化管理 | 模板变更仅影响新签合同，存量合同按签署时模板执行；模板要素变更留痕可追溯 |
| 合同在线签署 | 租户在线阅读合同全文→确认签约信息→电子签名→平台与租户双方签章→合同生成PDF存证；支持合同在线下载 | 签署前完成人脸识别核验（小程序/公众号端）；签署链接限时有效；签署完成不可篡改 |
| 合同状态管理 | 待签署、待生效、履行中、待续签、已到期、已解除、已作废全状态机管理；定时任务自动处理到期提醒、超时未签作废、押金超时解约 | 状态流转均有触发条件与留痕；解除/作废须记录原因；状态变化联动房源状态与账单停止生成 |
| 续租办理 | 用户端发起续租→系统校验（人才公寓/保租房：资格+欠费；市场租赁：仅欠费）→在线签署续租合同→管理端续租审批→租金缴纳提示 | 续租合同租期与原合同无缝衔接；校验不通过明确提示原因；原合同到期前设置续租提醒窗口 |
| 合同台账 | 常态化合同与集中合同统一台账：多条件查询（项目/业态/状态/租期/租户）、导出、详情追溯（签署记录/账单记录/变更记录） | 导出受权限控制并留痕；集中合同关联配租批次信息 |
| 我的合同（用户端） | 合同列表与详情：合同要素、签署状态、关联账单入口、续租入口、合同下载 | 市场租赁新签约合同展示签约倒计时；仅本人合同可见 |
| 合同备案（代购补贴） | 用户端发起合同备案（上传备案材料）→管理端备案审批→备案进度查询 | 备案通过方可发起代购补贴申请；审批意见回传用户端 |
| 合住人管理 | 用户端提交合住人申请（合住人身份信息）→管理端审批→合住人信息关联合同 | 合住人数量受房型限制；合住人身份信息脱敏展示 |
| 调换房管理 | 用户端提交调换房申请→管理端审核→审核通过后办理换房手续（原房源释放、新房源签约） | 换房前须结清原房源账单；原合同与新合同关联可追溯 |

**电子签章集成设计**：采用模板化签署流——系统预置合同模板与签署控件位置，签约时自动填充合同要素（租户信息、房源信息、租金、租期、押金），发起签署流后由租户完成个人签名、平台完成企业签章；签署状态通过回调+主动回查双通道同步；已签合同文件加密存证，支持司法举证调取。

### 2.5.3 支付管理

**设计概述**：支付管理是资金往来的核心域，覆盖"账单生成→在线支付→对账→退款→催缴→开票"完整资金链路，对接港区支付接口。设计目标：账单准确、资金安全、每一分钱可对账可追溯。

逐项功能设计如下：

| 功能点 | 功能设计说明 | 关键业务规则 |
|---|---|---|
| 押金账单 | 合同签署后自动生成押金账单，用户端在线缴纳；押金缴纳设时限并联动材料上传要求 | 超时未缴自动退押金、取消合同、释放房源；押金金额取自合同模板配置 |
| 租金账单 | 按合同付款周期自动拆分生成租期账单（账期起止、应缴金额、缴费截止日）；支持账单详情查看 | **押金账单未缴清前，租期账单不可选择缴费**；账期拆分精确到日，首末期按天数折算 |
| 在线支付 | 对接港区支付接口发起第三方在线支付：下单→跳转支付→回调确认→账单核销；支持优惠券抵扣计算 | 支付订单状态机严格管理（待支付/支付中/已支付/已关闭/已退款）；回调验签+幂等处理；超时订单自动关闭 |
| 优惠计算 | 缴费时自动匹配用户可用优惠券，计算抵扣金额并展示实付金额 | 优惠券使用规则（适用范围/有效期/面额）严格校验；一笔账单限用规则可配置；核销记录留痕 |
| 主动对账 | 每日定时与支付渠道对账单比对：平台订单与渠道流水逐笔核对，差异生成对账异常清单 | 差异账单冻结自动核销，人工处理后闭环；对账结果日报留存 |
| 退款管理 | 退租结算/超时退押场景发起退款申请→（撤销）→管理端审批→调用渠道退款→退款结果确认→凭证留存 | 退款按原账单明细拆分执行、原路退回；退款单与原支付单强关联；审批留痕 |
| 账单催缴 | 逾期账单自动标记，管理端支持单笔/批量催缴，触发消息通知（站内信/模板消息/短信可配置）；催缴历史记录 | 逾期规则（宽限期）可配置；催缴频次受限防骚扰 |
| 项目收款台账 | 按项目/按月统计应收、实收、逾期、退款，支持导出 | 台账口径与账单明细严格一致，支持追溯到单笔账单 |
| 开票管理 | 用户端按账期申请开票（选择已缴账期）→管理端受理并上传发票文件→用户端发票预览与下载；开票记录全程可查 | 同一账期不可重复申请开票；发票文件与账单关联存档 |
| 企业在线缴费 | 企业客户对集中分配房源批量缴费：企业信息+房源清单+账期汇总缴纳 | 企业缴费生成汇总支付单，核销时拆分回写各房源账单 |

**资金安全三重保障机制**：

1. **支付状态机**：订单状态流转严格受控，同一账单不允许并发生成多个有效支付单，从源头防止重复支付；
2. **回调兜底**：支付回调幂等处理（同一回调多次到达仅生效一次）；定时任务主动查询支付渠道订单状态，补偿回调丢失场景，确保"渠道已扣款、平台未核销"的账单最终一致；
3. **每日对账**：以渠道对账单为基准逐笔核对，差异当日告警、专人处理、处理结果留痕，实现资金零差错闭环。

## 2.6 系统接口设计

### 2.6.1 接口设计原则

统一采用 RESTful 风格 + JSON 报文；接口全部纳入 OpenAPI 3.0 在线文档；外部接口一律通过适配器层封装，做到"外部协议变化不侵入业务代码"；所有接口调用记录日志（请求方、时间、参数摘要、结果、耗时），可查可追溯。

### 2.6.2 郑好办用户体系对接

采用 OAuth2 授权模式对接郑好办统一用户体系：用户在移动端发起登录→跳转郑好办授权→回调携带授权码→后端换取访问令牌→获取用户身份信息→本地建立/关联用户档案→颁发系统 JWT 会话。令牌获取采用双重检查锁+Redis 缓存机制，避免并发重复请求；令牌到期自动刷新。对接时序如下图所示：

![图2-6 郑好办用户体系对接时序图](images/08-郑好办对接时序图.png)

郑好办对接接口逐项定义如下：

| 接口 | 方向 | 触发场景 | 关键请求要素 | 关键响应要素 | 异常处理 |
|---|---|---|---|---|---|
| 授权跳转 | 本系统→郑好办 | 用户点击登录 | 应用标识、回调地址、状态码 | 授权页跳转 | 跳转失败提示重试，记录失败日志 |
| 授权码回调 | 郑好办→本系统 | 用户完成授权 | 授权码、状态码 | — | 状态码校验防CSRF；授权码一次性使用 |

| 用户信息获取 | 本系统→郑好办 | 令牌换取成功 | 访问令牌 | 用户实名信息（姓名、证件号、手机号） | 信息不全时引导用户补充；采集留痕 |

### 2.6.3 政务数据资格核验对接

通过政务接口代理网关对接社保（郑州市）、婚姻（郑州市）、学历（郑州市）、住房（港区）、保租房（港区）5类核验接口以及房管局、不动产权中心公共数据接口：

- 代理网关部署于可访问政务网络的环境，统一鉴权、统一报文转换、统一日志留痕；
- 核验结果结构化落库并缓存，支持用户手动刷新重新核验；
- 接口不可用时自动降级人工审核通道，业务不中断；
- 敏感个人信息按最小必要原则调用，传输全程加密。

资格核验接口逐项定义如下：

| 接口 | 数据层级 | 核验内容 | 调用时机 | 结果处理 | 降级策略 |
|---|---|---|---|---|---|
| 社保信息核验 | 郑州市级 | 参保状态、缴费单位、连续缴费情况 | 资格校验发起/用户手动刷新 | 结构化落库，比对准入规则输出符合/不符合项 | 接口超时重试2次后转人工审核 |
| 婚姻信息核验 | 郑州市级 | 婚姻登记状态 | 同上 | 同上 | 同上 |
| 学历信息核验 | 郑州市级 | 最高学历、毕业院校 | 同上 | 同上 | 同上 |
| 住房信息核验 | 港区级 | 本区自有住房情况 | 同上 | 同上 | 同上 |
| 保租房信息核验 | 港区级 | 是否已承租保租房 | 同上 | 同上 | 同上 |
| 房管局公共数据 | 市/区级 | 房屋登记相关信息 | 业务按需调用 | 结果留痕 | 人工核查兜底 |
| 不动产权中心数据 | 市/区级 | 不动产权属信息 | 业务按需调用 | 结果留痕 | 人工核查兜底 |

**核验结果缓存与刷新机制**：核验结果设置有效期缓存，有效期内重复校验直接返回缓存结果不再调用政务接口，降低政务接口压力；用户点击"手动刷新"强制穿透缓存重新调用；每次核验的调用时间、数据来源、比对结论完整留痕，支撑资格审核的事后追溯。

### 2.6.5 内部接口与数据交换

前后端接口统一网关入口、统一响应结构（代码/消息/数据三段式）、统一异常处理；批量数据交换（房源导入、租户导出、迁移数据）采用模板化 Excel + 异步任务 + 结果回执模式，保证大批量数据处理不阻塞在线业务。

**接口规范细则**：

1. **命名规范**：URL 按"/模块/资源/动作"层级组织，资源名用名词复数，动作语义由 HTTP 方法表达（GET查询/POST新增/PUT修改/DELETE删除）；
2. **报文规范**：请求与响应统一 UTF-8 编码 JSON 报文；时间格式统一 yyyy-MM-dd HH:mm:ss；金额统一以分为单位的整数传输，杜绝浮点精度问题；
3. **分页规范**：列表接口统一 pageNum/pageSize 入参与 total/rows 出参结构；
4. **鉴权规范**：所有业务接口携带 JWT 令牌，网关统一校验；开放回调类接口采用签名验签+IP白名单双重防护；
5. **幂等规范**：所有写操作接口支持幂等（业务唯一键约束或幂等令牌），防止网络重试导致的重复提交；
6. **版本规范**：接口版本化管理，新版本上线保持旧版本兼容过渡期，避免多端发版不同步导致的接口不可用。

### 2.6.6 接口异常处理与容错设计

针对外部接口不可用、超时、返回异常三类故障场景，统一容错设计如下：

| 外部接口 | 故障场景 | 容错策略 | 用户侧体验 |
|---|---|---|---|
| 郑好办认证 | 授权服务不可用 | 已登录会话不受影响；新登录友好提示稍后重试 | 明确的错误提示与重试入口 |
| 政务核验 | 超时/不可用 | 重试2次→自动降级人工审核通道 | 提示"已转人工审核"，业务不中断 |
| 支付渠道 | 回调丢失 | 定时任务主动查单补偿，保证最终一致 | 支付结果页轮询，短暂延迟后正确显示 |
| 支付渠道 | 下单失败 | 幂等重试；持续失败则账单保持待缴状态 | 提示重试，账单状态不错乱 |
| 电子签章 | 签署流异常 | 回调+回查双通道；超时作废可重新发起 | 签署状态透明，可重新发起 |
| 人脸识别 | 识别服务异常 | 有限次重试；持续失败转人工核验通道 | 提示改用人工核验，流程可继续 |
| 地图服务 | 加载失败 | 前端降级为列表模式 | 找房功能不中断 |
| 园区监控 | 视频源中断 | 管理端标注离线状态，恢复自动重连 | 不影响其他业务 |

**熔断与隔离**：外部接口调用统一设置超时（连接/读取分离配置）与熔断阈值，故障接口快速失败不拖垮主线程池；各外部依赖独立线程池隔离，单一外部故障不产生雪崩效应。所有异常调用记录接口日志并触发告警，供运维快速定位。

## 2.8 系统安全设计

系统安全设计贯穿身份认证（郑好办统一认证+JWT+会话管理）、访问控制（RBAC菜单/按钮/数据三级权限）、传输安全（全站HTTPS）、数据安全（敏感字段加密存储、脱敏展示）、应用安全（SQL注入/XSS/CSRF防护、接口签名与幂等）、审计安全（登录/操作/接口日志全留痕）六个层面，整体按照网络安全等级保护二级标准设计建设。详细安全解决方案见本方案第四章"系统安全管理"。

应用层关键场景的安全设计要点如下：

| 安全场景 | 威胁 | 设计措施 |
|---|---|---|
| 登录认证 | 凭证窃取、会话劫持 | 郑好办统一认证，本系统不存密码；JWT短有效期+刷新机制；同账号异常登录检测 |
| 越权访问 | 水平/垂直越权 | 接口级鉴权+数据行级权限双重校验；用户端接口强制校验数据归属（仅本人合同/账单可见） |
| 支付安全 | 金额篡改、重复支付、伪造回调 | 金额以服务端账单为准不信任前端；订单状态机+幂等；回调验签+IP白名单 |
| 文件上传 | WebShell、带毒文件 | 类型白名单+内容检测+重命名+隔离存储+禁执行权限 |
| 敏感数据 | 泄露、滥用 | 证件号/手机号加密存储、界面脱敏；导出脱敏与权限控制；最小必要采集 |
| 接口滥用 | 爬取、刷单、短信轰炸 | 限流、验证码、频次控制；关键操作行为日志分析告警 |
| 前端安全 | XSS、CSRF | 输入输出双向过滤转义、CSP策略、Token校验、敏感操作二次确认 |
